# sub_180002240 (WS-body packer) — decompilation

Authoritative synthesis of parallel decodes of the WS-body packer in `synaWudfBioUsb.dll`
(x86-64, Windows x64 ABI). This is the per-frame appender that the enrollment driver
`sub_1800D89C0` calls once per captured frame to fold one feature set into the growing WS body.

---

## 1. Signature & role

**Confirmed signature**

```c
int32 __fastcall sub_180002240(
    void *algo,             // RCX -> RSI : algorithm/session handle (NOT the WS body)
    void *ws_dest,          // RDX -> R15 : WS-body destination / stream container  <-- THE WS BODY
    struct frame_stats *stats, // R8 -> RDI : per-frame outcome struct (NOT the WS body)
    void *features,         // R9         : extracted-feature buffer (250 kp + 16B desc, the v30 source)
    int32 w,                // [rsp+0x140] (arg5) : image width
    int32 h);               // [rsp+0x148] (arg6) : image height
// returns EAX = r12d (0 on early-out/readiness fail, else the worker sub_180001fe0 result)
```

**Which arg is the WS-body / session struct**

- **`ws_dest` (RDX, arg2)** is the WS-body destination. It is passed as RDX to the stream-cursor
  constructor `sub_1800068f0` (at `0x180002291`, `0x1800022f4`), as R8 to the main worker
  `sub_180001fe0` (at `0x1800024ad`), and as RCX-equivalent to the codec cluster via the
  `[rsp+0x50]` cursor that was built over it. This matches prior RE (`session+152`) and the gdb hook
  that read RDX as the WS body.
- **`algo` (RCX, arg1)** is the algorithm/session handle. It owns the persistent cross-frame
  accumulator (`*(algo+8)` -> `sub_180001000` -> RBX) and the limits sub-context `*(algo+0x30)` -> R14.
- **`stats` (R8, arg3)** is a per-frame outcome struct (reject flags, counts, sizes) returned to the
  caller — not the WS body.

**Purpose (one paragraph).** Per-frame WS-body section appender. On each call it (1) checks the
algorithm-ready gate `sub_180001010`; (2) builds two stream cursors over `ws_dest` into stack scratch
at `[rsp+0x50]`/`[rsp+0x78]`; (3) on the **first frame only** writes the 3-byte sensor/algo ID
(CONST `[16..24)`) via `sub_1800066f0` and sets the persistent first-frame guard `[rbx+0x144]=1`;
(4) fetches the persistent 180-byte-per-record enrollment stream via `sub_180003320`; (5) reads TLV
config fields (tags `0x0a`, `0x12`, `0x06`) via `sub_180001750`; (6) runs the heavy per-frame worker
`sub_180001fe0`, which decides accept/reject and builds the working records + POSE summary; (7) if
accepted, emits **one** v30 section into the WS body through the `sub_18005xx`/`sub_18006xx` codec
cluster, keyed by an incrementing section index `EBP`; (8) finalizes `stats` and tears down/commits the
cursor via `sub_180006080`/`sub_180001d80`. The multi-frame merge into 5 consolidated sections is
driven by **repeated calls from the caller**, not by an internal loop here.

## 2. Control flow

**No internal frame loop.** The function is straight-line: every conditional jump targets a *forward*
address. There is exactly **one frame / one section per invocation**. The "loop over frames" lives in
the caller `sub_1800D89C0`.

Internal small loops live only in callees:
- The codec emitters (`sub_1800051f0`, `sub_1800053e0`, `sub_180001df0`) loop over **per-section
  records / minutiae rows** (stride 20 bytes), building the v30 record body and the inter-record
  relationship matrix.
- The worker `sub_180001fe0` loops over **keypoints** (N records, stride 0xb4=180) via the descriptor
  engine `sub_180008f10` and the threshold post-pass.

So three nesting levels exist conceptually but only one is in *this* function:
`frames` (caller) → `sections` (this function, one per call, index `EBP`) → `keypoints/records`
(callees).

**Compact pseudocode skeleton** (addresses are call/branch sites)

```c
int32 sub_180002240(algo, ws_dest, stats, features, w, h) {
  r12d = 0;
  if (sub_180001010(algo) != 1) return 0;                 // 0x180002268 readiness gate

  cur1 = sub_1800068f0(&[0x78], ws_dest, 0);               // 0x1800022a1 build cursor#1
  copy16(&[0x50], cur1);
  sub_180006130(algo, &[0x50]);                            // 0x1800022c1 attach cursor to algo
  r14 = *(algo+0x30);                                      // limits/config sub-ctx
  sub_180001d30(stats);                                    // 0x1800022cd zero stats
  rbx = sub_180001000(*(algo+8));                          // 0x1800022d6 PERSISTENT state obj

  firstframe = (*(u32*)(rbx+0x144) == 0);
  cur1 = sub_1800068f0(&[0x78], ws_dest, firstframe);      // 0x1800022f4 rebuild (init hdr on frame 0)
  copy16(&[0x50], cur1);

  if (*(u32*)(rbx+0x144) == 0) {                           // 0x18000230c one-shot init
    *(u32*)(rbx+0x144) = 1;                                // 0x180002315 guard set
    sub_1800066f0(&[0x50], algo[0], algo[1], algo[2]);     // 0x180002331 write CONST id [16..24)
  }

  ebp  = sub_180005b90(&[0x50]);                           // 0x18000233b sections-so-far index
  r13d = sub_180005cd0(&[0x50]);                           // 0x180002347 secondary counter
  if (ebp == sub_1800013d0(algo)) goto finalize;           // 0x180002357 target (5) reached -> skip emit

  fcur = sub_180006680(&[0x90], features);                 // 0x18000236f cursor over features
  copy24(&[0x78], fcur);
  eax = sub_180005fc0(&[0x78]);                            // 0x180002394 keypoint count
  stats.reject = 0; stats.kp_count = eax;
  if (eax < *(s32*)(r14+0x30)) { stats.reject=1; rbx[0x130]++; } // 0x1800023a0 too-few -> reject + accum

  // stage persistent buffer ptrs + w*h into the algo work-header
  rec = sub_180003320(&[0x90], &[0x68], r14[0x10]*0xb4);   // 0x1800023f1 persistent 180B record stream
  copy48(&[0xc0], rec);
  (*(algo+0x48))([0x68], 0, r14[0x10]*0xb4);               // 0x18000243e vtable: zero new region

  sub_180001750(algo, 0x0a, &[0x70]);                      // 0x18000244e TLV tag 0x0a
  sub_180001750(algo, 0x12, &[0x74]);                      // 0x180002460 TLV tag 0x12

  r12d = sub_180001fe0(algo, features, ws_dest, stats, ... // 0x1800024ad MAIN worker -> return value
            [0x20]=tag0x12, [0x28]=&[0x60], [0x30]=ebp,
            [0x38]=algo, [0x40]=&[0xc0], [0x48]=tag0x0a);

  if (stats[0x18]) { r13d++; sub_180005cb0(r13d,&[0x50]); stats.reject=1; } // 0x1800024b2
  if ([0x60] == 1) stats.reject = 1;                       // 0x1800024d3
  sub_180001750(algo, 0x06, &[0x64]);                      // 0x1800024ee TLV tag 0x06 (capacity)
  if ((u16)cur2[2] + cur1[4] > [0x64]) stats.reject = 1;   // 0x180002505 capacity guard

  if (stats.reject == 0) goto emit;                        // 0x180002512
  if (stats[0x18] == 0) goto cleanup;                      // 0x180002518 rejected -> maybe skip
  if (r14[0x2c] == 0)   goto cleanup;                      // 0x180002522 forced-emit-on-reject flag

emit:                                                      // ===== EMIT ONE v30 SECTION =====
  ebp++;                                                   // 0x18000253d section index ++
  sub_1800053e0(&[0x50], rbx[0x138], r14[0x10]);           // 0x180002540 type-2 TLV sub-record
  sub_180001df0(ebp, (u8)stats[0x14], [0x68], rbx[0x138]); // 0x18000255a relationship-matrix builder
  sub_1800051f0(rbx[0x138], ebp, r14[0x10], &[0x50], algo[0x10]); // 0x180002576 v30 records + POSE leads
  sub_1800056c0(features, ebp, &[0x50]);                   // 0x180002585 TLV record (tag = ebp+3)
  sub_180005ba0(0, &[0x50]);                               // 0x180002591 setter tag 0x68
  sub_180005b70(ebp, &[0x50]);                             // 0x18000259d setter tag 0x03
  sub_180005bd0(h, w, &[0x50]);                            // 0x1800025b5 TLV tag 0x69 (two u32: h,w)
  sub_180005ce0(r14[0x10], &[0x50]);                       // 0x1800025c3 setter tag 0x6b (count)

cleanup:
  sub_180006080(algo, &[0x50]);                            // 0x1800025d0 TLV tag 0x6c (4 u32 counts) + commit

finalize:
  stats[0x24]=ebp; stats[0x34]=r13d; stats[0x38]=[0x60];
  stats[0x20]=cur1[4]+0x0c;                                // body size + 12-byte TLV header
  sub_180001d80(algo, stats);                              // 0x1800025f7 finalizer: bitmask+percent
  return r12d;
}
```

## 5. Multi-frame accumulator verdict

**Verdict: the accumulator is NOT inside `sub_180002240`.** It lives in objects this function *fetches*
from the `algo` handle and *persists across calls*. This function is invoked once per frame with no
internal frame loop.

Evidence:
1. **No backward branches** — every conditional jump is forward; one section per call (control_flow).
2. **`rbx = sub_180001000(*(algo+8))`** at `0x1800022d6` returns the **same persistent state object**
   every call.
3. **First-frame guard `[rbx+0x144]`** — read at `0x1800022e3` / `0x18000230c`, set to 1 at
   `0x180002315`. It is 0 only on the very first frame, proving `rbx` survives across calls.
4. **`[rbx+0x130] += 1`** at `0x1800023ad` is a reject counter that *increments across frames*.
5. **`[rbx+0x138]`** (persistent section/record buffer) is passed to the writer cluster at
   `0x180002540`, `0x18000255a`, `0x180002576` — the buffer into which sections accumulate.
6. **`[rbx+0x148]`** persistent buffer ptr stored into the work header at `0x1800023c4`/`0x1800023c8`.
7. **`sub_180003320`** at `0x1800023f1` returns the persistent 180-B-per-record stream (the actual
   frame-merge backing store; sized `r14[0x10]*0xb4`).
8. **Section index `EBP`** is fetched fresh each call via `sub_180005b90` (`0x18000233b`) and compared
   to the target (5) from `sub_1800013d0` (`0x180002357`); when equal, emit is skipped. The 5-section
   consolidation is reached by *repeated calls advancing EBP*, not a loop.
9. The worker `sub_180001fe0` bumps a session accept-counter `[rsi+0x130]` (where `rsi=*(algo+8)`),
   another cross-frame accumulator.

**Where to decode next for the accumulator merge logic:** the persistent-state holder behind
`*(algo+8)` and the buffer at `[rbx+0x138]` / `[rbx+0x148]`. The functions that *populate* those across
frames are the worker `sub_180001fe0` (and its descriptor engine `sub_180008f10`, **not yet dumped**)
plus `sub_180003320`'s backing store. To see the merge in action, decode **`sub_180008f10`** (owns the
`[309..4809)` v30 record region per the WS layout) and hook `[rbx+0x138]`/`[rbx+0x148]` across frames.

## 6. The 8-byte ascending "POSE" leads

**Best hypothesis:** the 8 ascending lead bytes per section are produced inside **`sub_1800051f0`** by
its sort/permute helper **`sub_18000bd10`** (called at `0x18000522c` with `edx=0x333`, `r8d=0x12c=300`,
`r9d=1`). `sub_18000bd10`:
1. reads the count byte `BYTE[obj+0x10]`,
2. builds a paired index array at `[rsp+0x60]`,
3. sorts it via `sub_1800095c0`,
4. **permutes the bytes at `*(obj+0)` into ascending order**.

`sub_1800051f0` then emits those (now monotonically ascending) bytes as the first `N` bytes of the
section header via `sub_180006550` at `0x18000526b` (put-N-bytes from `*(obj+0)`). This precisely
explains the observed "8 ascending bytes that vary per session+section": they are the **sorted order of
a per-section, session-derived byte vector** (the object's `+0` source array), with the count from
`obj+0x10`.

The *values* in `*(obj+0)` originate upstream: `sub_180001df0` (`0x18000255a`) builds the in-memory
inter-record relationship matrix with clamped score bytes (`0x7fff→0xff`), and `sub_180001fe0`'s POSE
summary (`+4 poseX`, `+8 poseY`, `+0x10 score`) feeds the per-section pose. The lead bytes are most
likely the **sorted quality/score bytes** of the section's records, not raw coordinates.

**How to confirm:**
- **NEEDS-HOOK:** dump `*(obj+0)` (length = `BYTE[obj+0x10]`) **before and after** the
  `sub_18000bd10` call at `0x18000522c`, and compare the post-sort bytes against the ascending leads

## 7. Contradictions / low-confidence items

1. **`sub_180005ce0` byte width.** The tiny-helper decode says `sub_180005ce0` is a thunk to
   `sub_180006b80` with tag `0x6b`. The packer-level note labels it "per_section_counts finalizer
   `[24..40)`". Both can be true (it writes a single count value tagged 0x6b that becomes part of the
   per-section count framing), but whether it writes a *u32 to `[24..40)`* or a smaller tagged field is
   **unresolved**. Decode `sub_180006b80` to settle.

2. **`per_section_counts [24..40)` writer ambiguity.** Two candidates: `sub_180006080` (tag-0x6c,
   4×u32, session-derived from `algo+0x130..0x154`) vs `sub_180005ce0` (tag-0x6b, `r14[0x10]` per
   section). They may write *different* fields that both feed the consolidated counts. NEEDS-HOOK on the
   `[rsp+0x50]` builder to attribute bytes.

3. **`sub_180005ba0` arg.** Packer notes call it "flush/marker, rcx=0". The thunk decode shows it is a
   tag-0x68 setter taking `(value=ecx, ptr=rdx)` with arg swap, so `rcx=0` means it writes value 0
   under tag 0x68. "Flush/marker" is the packer agent's guess; the thunk decode (tag-0x68 setter) is
   more authoritative. Treat as a **setter writing 0 under tag 0x68**, not a flush.

4. **`writes_dest_buffer` for `sub_1800056c0`.** Its own decode says `false` (it mutates the *source*
   buffer header and delegates the actual stream write to `sub_180006a80`), yet it clearly contributes
   bytes to the WS stream via that callee. Classified here as "Yes (via `sub_180006a80`)" — the
   `writes_dest_buffer:false` is literally true (no direct store) but misleading at the WS level.

5. **`sub_180001fe0` `writes_dest_buffer:true`.** Marked true, but it writes the *POSE summary record*
   (arg4) and *working records* (arg1), **not** the 23056-byte WS body. Do not count it as a WS writer;
   its outputs are *consumed* by the codec cluster later.

6. **`size_u32` exact write site.** Static decode strongly links it to the id-6 formula and the commit
   path, but the precise instruction that stores `0x59fc` into `[4..8)` is **not in this function**.
   Likely inside `sub_180006080` or the cursor finalize in `sub_1800068f0`/`sub_1800067e0`. NEEDS-HOOK.

7. **`[8..16)` config constant origin.** Assumed to be a constant table copied during first-frame
   header init inside `sub_1800067e0` (undumped). No instruction-level proof yet.

### 9.2 POSE leads — REFUTED (it's an argsort/index permutation)

Pointer-flow spine TRUE: `sub_1800051f0` calls `sub_18000bd10(obj)` @`0x18000522c`, then put-N from `*(obj+0)` via `sub_180006550` @`0x180005276` (same buffer). But `bd10` is an **argsort**:
- @`0x18000bd60` overwrites `*(obj+0)` with identity `0..N-1`;
- @`0x18000bd80` builds a 2-byte temp `{key=const 0x00, idx=i}` at `[rsp+0x60]`;
- @`0x18000bda6` sorts via `sub_1800095c0` (generic introsort), comparator `0x18000b1f0` returns `b0-a0` = **descending convention**, primary key uniformly `0x00` so only the index tiebreak acts;
- @`0x18000bdc1` writes `(*(obj+0))[i] = sorted_temp[i].idx`.

So the emitted leads are an **index/rank permutation**, not sorted score bytes; "ascending" is incidental to the identity init. The put-N **count = `edi` = arg3** (saved `0x18000520d`), **not** `BYTE[obj+0x10]` (=arg2, stored `0x180005210`). The real ranking data lives in `obj+0x8`/`obj+0x11`, populated by `sub_18000bbe0` (`0x18000bc70`/`0x18000bce6`). **NEEDS-HOOK** (`GDB_DUMP_POSE`) to link the permutation to actual pose scores.

### 9.3 per_section_counts — PARTIAL (mechanics confirmed, offset & order corrected)

## 10. Static correction — `sub_1800051f0` does NOT emit the 4500-byte v30 content
