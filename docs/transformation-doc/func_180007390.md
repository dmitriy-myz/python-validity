# sub_180007390 — 4-dword "compute then pack into out-struct" wrapper

Thin adapter around the real worker `sub_180006e10`. It allocates a local
scratch frame, hands the worker **four output pointers** (one in `rcx`, three
laid out on the stack), and on success copies the four resulting `int32`s into
the caller-supplied 16-byte output struct (`rcx`/`rbx`). Returns 1 on success,
0 on failure.

The worker `sub_180006e10` is where the actual transform/coord math lives; this
function is purely glue. The interesting RE detail is the **field mapping**: the
worker's 4 outputs are written to out-struct offsets `+0x0, +0x4, +0x8, +0xc`,
but the source slots are *interleaved* (the `rcx`-output slot `[rsp+0x68]` maps
to `[rbx+0x0]`, while the contiguous `[rsp+0x30..0x38]` triple maps to
`[rbx+0x4..0xc]`).

## Pseudocode

```c
BOOL sub_180007390(out16_t *out /*rcx*/, void *arg_rdx /*rdx*/, void *arg_r8 /*r8*/)
{
    // ---- prologue ----                                        // 0x180007390
    //   push rbx ; sub rsp,0x40                                 // 0x180007390 / 0x180007392
    //   [rsp+0x28] = r8                                         // 0x180007396  (spill arg_r8)
    //   rbx = rcx  (save out ptr)                               // 0x18000739b
    //   [rsp+0x20] = rdx                                        // 0x1800073a0... actually 0x18000739e (spill arg_rdx)

    // ---- set up worker call ----
    // The worker sub_180006e10 takes 4 pointer args (rcx,rdx,r8,r9), each
    // pointing at an int32 output slot in this frame:
    int32_t s_30, s_34, s_38, s_68;
    //   rdx = &s_30   (lea rdx,[rsp+0x30])                      // 0x1800073a3
    //   r9  = &s_38   (lea r9,[rsp+0x38])                       // 0x1800073a8
    //   r8  = &s_34   (lea r8,[rsp+0x34])                       // 0x1800073ad
    //   rcx = &s_68   (lea rcx,[rsp+0x68])                      // 0x1800073b2
    int eax = sub_180006e10(&s_68 /*rcx*/, &s_30 /*rdx*/,
                            &s_34 /*r8*/,  &s_38 /*r9*/);        // 0x1800073b7  (call 0x180006e10)
    //   NOTE: arg_rdx/arg_r8 spilled at [rsp+0x20]/[rsp+0x28] are NOT passed in
    //   registers here; the worker reads them off the caller's frame OR they are
    //   dead. See open questions.

    if (eax == 0)                                                // 0x1800073bc test / 0x1800073be je
        goto L_fail;                                             // -> 0x1800073e6

    // ---- success: pack 4 int32 outputs into out[0..3] ----
    out->f0 = s_68;   // *(int*)(rbx+0x0) = [rsp+0x68]           // 0x1800073c0 / 0x1800073c4
    out->f4 = s_30;   // *(int*)(rbx+0x4) = [rsp+0x30]           // 0x1800073c6 / 0x1800073ca
    out->f8 = s_34;   // *(int*)(rbx+0x8) = [rsp+0x34]           // 0x1800073cd / 0x1800073d1
    out->fc = s_38;   // *(int*)(rbx+0xc) = [rsp+0x38]           // 0x1800073d4 / 0x1800073d8

    return 1;         // mov eax,1                               // 0x1800073db
    // add rsp,0x40 ; pop rbx ; ret                              // 0x1800073e0 / e4 / e5

L_fail:                                                          // 0x1800073e6
    return 0;         // xor eax,eax                             // 0x1800073e6
    // add rsp,0x40 ; pop rbx ; ret                              // 0x1800073e8 / ec / ed
}
```

No coordinate/fixed-point math is performed *in this function*. No shifts,
multiplies, trig, sort, or loops — it is straight-line glue plus one branch.

## GDB verification hooks

For a Python re-implementation, the critical thing to capture is the I/O of the
worker call and the final packed struct.

- `break *0x1800073b7`  — **immediately before** the `call 0x180006e10`.
  - Dump `$rcx` (= `&out#0` slot, `rsp+0x68`), `$rdx` (`rsp+0x30`),
    `$r8` (`rsp+0x34`), `$r9` (`rsp+0x38`) — these are the 4 output pointers.
  - Dump the two spilled inputs: `x/wx $rsp+0x20` (arg_rdx) and
    `x/wx $rsp+0x28` (arg_r8). Also record original `arg_rdx`/`arg_r8` pointer
    values and, if they are pointers, deref a few words to capture the worker's
    actual inputs.
  - Record the saved out-struct base: `$rbx`.

- `break *0x1800073bc`  — **immediately after** the call returns.
  - `p/d $eax` — worker success flag (1 = will pack, 0 = fail/return 0).
  - If `eax != 0`, dump all four result slots in one go:
    `x/4wx $rsp+0x30` (gives `[+0x30]=out1, [+0x34]=out2, [+0x38]=out3, [+0x3c]`)
    and separately `x/wx $rsp+0x68` (= out0). These four int32s are the
    transform/coord outputs to match against Python.

- `break *0x1800073db`  — **after** the four stores, before `ret` (success path).
  - `x/4wx $rbx` — final packed output struct
    `{out->f0, out->f4, out->f8, out->fc}` =
    `{[rsp+0x68], [rsp+0x30], [rsp+0x34], [rsp+0x38]}`. Confirms the
    interleaved field mapping.

- `break *0x1800073e6`  — failure path entry (worker returned 0). If hit, the
  out struct is left untouched and the function returns 0.

## Confidence & open questions

Solid:
- Control flow, the single branch, and both return values (1/0) are
  unambiguous.
- The four output slots and their **exact** mapping to `out+0x0/4/8/c` are
  certain from the disasm; note the deliberate interleave (`+0x68`→`+0x0`,
  `+0x30/34/38`→`+0x4/8/c`).
- Each field is a raw 32-bit copy (no extension).

Inferred / open:
- **Where do `arg_rdx` and `arg_r8` go?** They are spilled to `[rsp+0x20]` and
  `[rsp+0x28]` but are **not** loaded into argument registers before the
  `call`. Either (a) `sub_180006e10` reads them from the caller's home/shadow or
  this frame by convention, or (b) they are this function's own incoming args
  homed for the worker to fetch via a known offset, or (c) they are dead. Cannot
  resolve without decompiling `sub_180006e10`. This is the main unknown.
- Semantic meaning of the four output int32s (e.g. `{flag,a,b,t}` of a Q16
  similarity transform vs. `{x0,y0,x1,y1}` coordinates) is **not determinable
  here** — it lives entirely in `sub_180006e10`. The fact that one output
  (`+0x68`/`out->f0`) is segregated from the contiguous triple hints it may be a
  count/flag/score while the other three are a coordinate or (a,b,t) tuple, but
  that is a **guess**.
- Return type assumed `int`/`BOOL`.
