# sub_18000b3f0 — struct-field unpacking thunk into the byte-range validity predicate

A 7-byte, 3-instruction tail-call thunk (no stack frame, no locals). It takes a
pointer to a small struct/record in `rcx`, loads the record's first two bytes
(`[rcx+0]` and `[rcx+1]`), and tail-jumps into `sub_18000b3d0` with those two
bytes as the (a, b) arguments. So it is the "I have a pointer to the record"
convenience wrapper around the bare two-byte predicate.

It is **not** geometry / transform math itself. The thing it ultimately computes
is `sub_18000b3d0`'s boolean: `return ((uint8)byte0 > 0x1E) && ((uint8)byte1 <= 0x31)`,
i.e. `byte0 > 30 && byte1 <= 49`. This thunk only does the field unpacking and
the argument-register shuffle; the actual accept/reject logic lives in the callee.
It sits on the sec0_pre / template-build path as a per-record "is this (a,b) pair
in the allowed window?" guard, but produces no rigid-transform / Q16 quantities.

## Signature

```c
// rec points at a record whose first byte is "a" and second byte is "b".
// Equivalent to:  return sub_18000b3d0(rec[0], rec[1]);
//             i.e. return ((uint8)rec[0] > 0x1E) && ((uint8)rec[1] <= 0x31);
// (byte0 > 30 && byte1 <= 49)
BOOL sub_18000b3f0(const uint8_t *rec /*rcx*/);
```

Arg meaning (inferred — exact field semantics live in `sub_18000b3d0`'s callers):
- `rec` (rcx): pointer to a struct/record.
  - `rec[0]` (`[rcx+0]`) → becomes `cl` = predicate arg `a`; must be **> 30** to pass.
  - `rec[1]` (`[rcx+1]`) → becomes `dl` = predicate arg `b`; must be **<= 49** to pass.
- Return: `eax` = boolean (1 = both bounds satisfied, 0 = otherwise). The thunk
  itself does not touch `eax`; the tail-called `sub_18000b3d0` sets it.

Note the argument order is **swapped relative to load order**: the function loads
`[rcx+1]` into `edx` (= `b`) *first*, then `[rcx]` into `ecx` (= `a`). After the
loads, `ecx`=byte0 and `edx`=byte1, which is the natural `(a=cl, b=dl)` order the
callee expects. So `byte0` is the `a` (>30) field and `byte1` is the `b` (<=49) field.

## Pseudocode

```c
BOOL sub_18000b3f0(const uint8_t *rec /*rcx*/)
{
    // --- entry / single block : 0x18000b3f0 ---
    uint8_t b = rec[1];                 // 0x18000b3f0: movzx edx, BYTE PTR [rcx+0x1]  (edx = byte1, zero-extended)
    uint8_t a = rec[0];                 // 0x18000b3f4: movzx ecx, BYTE PTR [rcx]      (ecx = byte0, zero-extended)

    // Tail call: jmp (not call) — reuses this frame; callee's RET returns to OUR caller.
    return sub_18000b3d0(a /*cl*/, b /*dl*/);   // 0x18000b3f7: jmp 0x18000b3d0
    // i.e.  return ((uint8)rec[0] > 0x1E) && ((uint8)rec[1] <= 0x31);
}
```

Both loads are `movzx` (zero-extend), so the high bits of `ecx`/`edx` are cleared;
only the byte values matter and `sub_18000b3d0` inspects only `cl`/`dl` anyway.

## Callees

- `0x18000b3d0` — byte-range validity predicate; returns `(uint8)a > 30 && (uint8)b <= 49`.

## GDB verification hooks

This thunk has no intermediate math; verification is input capture (the output is
produced by the callee).

- `break *0x18000b3f0` (entry) — dump the record pointer and the two fields it will read:
  - `p/x $rcx` → record pointer `rec`.
  - `x/2xb $rcx` → the two bytes; first byte = `a` (compared > 30), second = `b` (compared <= 49).
  - Equivalent: `p/x *(unsigned char*)$rcx` (a / byte0) and `p/x *(unsigned char*)($rcx+1)` (b / byte1).

- `break *0x18000b3f7` (the `jmp`) — just before transferring to the callee, confirm
  the register marshalling:
  - `p/x $ecx & 0xff` → `a` (should equal `rec[0]`).
  - `p/x $edx & 0xff` → `b` (should equal `rec[1]`).
  This is the key point to verify a Python port: `a, b = rec[0], rec[1]`.

- The boolean result is set by `sub_18000b3d0`; to capture the final output, break at
  its returns (`*0x18000b3df` accept, `*0x18000b3e2` reject) and dump `p/x $eax`
  (1 = valid, 0 = invalid). Because this is a tail call, that `RET` returns directly
  to `sub_18000b3f0`'s caller, so `eax` at those points is this thunk's return value too.

Oracle test for a re-implementation:
`f(rec) = 1 if (rec[0] & 0xff) > 0x1E and (rec[1] & 0xff) <= 0x31 else 0`
must match the captured `eax` byte-for-byte across all calls.

## Confidence & open questions

**Solid (high confidence):**
- The exact behavior: load `rec[1]`→`edx`, `rec[0]`→`ecx`, tail-jump to `sub_18000b3d0`.
  All 3 instructions present; no hidden paths, no stack frame, no side effects.
- Zero-extending byte loads; no fixed-point / matrix / transform math in this function.
- It is a pure thunk; the accept/reject semantics are entirely in `sub_18000b3d0`
  (`byte0 > 30 && byte1 <= 49`).

**Inferred / open:**
- The *meaning* of `rec[0]` / `rec[1]` (and of the whole record `rec` points at).
  The function only fixes that field 0 is the ">30" field and field 1 is the "<=49"
  field. Whether these are counts, indices, dimensions, or class ids must be read
  from this thunk's callers and from `sub_18000b3d0`'s other callers
  (`sub_180007b30`, `sub_1800082a0`).
- This helper is on the template-build path but does **not** itself compute any
  rigid-transform / Q16 quantities relevant to `sec0_pre` frame registration.
