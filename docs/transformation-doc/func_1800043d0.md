# sub_1800043d0 — image/frame preprocessing + 4-stage feature pipeline orchestrator

This function is a **thin orchestrator** (no arithmetic of its own beyond one `imul`). It:
1. Reads ~9 arguments (4 in registers, 5 on the stack).
2. Allocates a big stack frame (0x4d8) holding **four 256-byte scratch buffers**
   (`buf0 @ rsp+0xc0`, `buf1 @ rsp+0x1c0`, `buf2 @ rsp+0x2c0`, `buf3 @ rsp+0x3c0`) plus
   two output slots for the first call (`out0 @ rsp+0x80`, `out1 @ rsp+0x90`).
3. Calls **6 subroutines** in sequence, threading the same scratch buffers and image
   dimensions (`w = arg6`, `h = arg7`, `w*h`) between them.
4. The middle/late calls are gated on a non-null `ctx` (rcx) **and** `*(int*)(ctx+0x20) != 0`.

It does **not** itself compute a transform. It is the per-frame driver that produces the raw
feature inputs the later transform/registration code consumes. The actual fixed-point /
matrix math lives in the callees (`sub_180003b50`, `sub_180003ea0`, `sub_1800041d0`).

> Frame layout note: 8 callee-saved pushes (0x40) + `sub rsp,0x4d8`, so an arg the caller
> placed at entry `[rsp+0x28+k]` is read here at `[rsp+0x540+k]`. All stack-arg offsets below
> were derived from that.

    void   *arg3_p,     // r8   (saved in r13) -> pointer threaded into calls (params/table? GUESS)

    uint8_t h,          // [rsp+0x550] -> r12d  image height / dim B        (GUESS)

`w*h` (`imul r8d,r12d`) is passed as the size/count argument (r8d) to the first call — strongly
suggesting `w`,`h` are the two image dimensions and the first call fills a `w*h` buffer.

### Important caveat on CALL #4 `r8`
At `18000450e` the code calls `sub_180004060` without an explicit `mov r8,...` after the
call#3 setup. `r8` therefore holds whatever value survived calls #1–#3 (the loader for call#3
last set `r8 = &rsp[0x1c0]`/buf1 at `1800044aa`, but `sub_1800041d0` may clobber it).
This is a register-inheritance ambiguity — **verify `r8` live at `0x18000450e` with gdb**
before trusting any porting assumption. (Most likely the compiler intends a buffer pointer or a
count; do not invent a value.)

## GDB verification hooks

Set these breakpoints (file base assumed `0x180000000`; rebase to the loaded module base if PIE):

1. **Entry / argument capture** — `break *0x1800043f6`
   After the prologue, dump the resolved args:
   - `x/1gx $rsp+0x540` → arg5 (rdx of call#1, src ptr)
   - `x/1bx $rsp+0x548` → `w`
   - `x/1bx $rsp+0x550` → `h`
   - `x/1gx $rsp+0x558` → arg8
   - `x/1gx $rsp+0x560` → arg9
   - `$rcx`=ctx, `$rdx`=arg2, `$r8`=arg3, `$r9`=arg4
   These pin the function's full input vector.

2. **w*h product** — `break *0x18000442f` (just after `imul r8d,r12d`)
   - `p/d $r8d` → must equal `w*h`. (Confirms dimension semantics.)

3. **Before call#1** — `break *0x18000444a`
   - `$rcx`=&out1, `$rdx`=arg5, `$r8d`=w*h, `$r9`=&out0 (`$rsp+0x80`).
   On return (`break *0x18000444f`): `x/1gx $rsp+0x80` = `out0` (the produced buffer ptr) and
   `x/1gx $rsp+0x88` = arg9 echoed.

4. **Gate** — `break *0x1800044cd`
   - `p/d *(int*)($rsi+0x20)` → `ctx->f20`. If 0, calls #4–#6 are skipped. Records the
     enable/count value reused later.

5. **Before call#3 (heavy stage)** — `break *0x1800044bf`
   Dump every buffer/arg so a Python port of `sub_1800041d0` can be diffed:
   - `$rcx`=buf3, `$rdx`=buf0, `$r8`=buf1, `$r9`=buf2
   - `x/12gx $rsp+0x20` → the 6 stacked args (&f20,&f24,arg2,arg3,arg4, w|h packed, out0)
   On **return** `break *0x1800044c4`: `x/64bx $rsp+0xc0`, `+0x1c0`, `+0x2c0`, `+0x3c0` to
   capture buf0..buf3 contents (the feature outputs).

6. **Before call#4** — `break *0x18000450e` **(critical: resolve the inherited `r8`)**
   - `p/x $r8` → record the actual value passed (clears the ambiguity noted above).
   - `x/1gx $rsp+0x28`=&f34, `+0x30`=&f38, `+0x38`=&f30.
   On return: `x/8bx $rsi+0x30` → the f30/f34/f38 tuple just written.

7. **Before call#5** — `break *0x180004565`
   - `$rcx`=&f08, `$rdx`=&f0c, `$r8`=arg2, `$r9`=arg3
   - `x/8gx $rsp+0x20` → stacked (w,h,buf0,buf1,buf2,f20,out0).
   On return `break *0x18000456a`: dump `x/16bx $rsi+0x08` (f08/f0c outputs).

8. **Before call#6** — `break *0x1800045cf`
   - `$rcx`=ctx, `$rdx`=&f04; `x/0x10gx $rsp+0x20` → all 11 stacked args incl. arg8/arg9.
   On return `break *0x1800045d4`: dump `x/16bx $rsi+0x04` and the three scratch buffers again
   to see the final cumulative state.

For each scratch buffer, dumping 256 bytes (`x/256bx <addr>`) gives the full window since the
buffers are 0x100 apart.

## Confidence & open questions

**Solid (directly from disasm):**
- Control flow, the 6 callee addresses and their exact argument registers/stack slots.
- The four 256-byte scratch buffers and their reuse pattern across calls.
- The gate: `ctx != NULL && *(int*)(ctx+0x20) != 0` enables calls #4–#6.
- `w*h` is computed once (`imul r8d,r12d`) and passed to call#1.
- `arg9` is pre-stored at `rsp+0x88` (adjacent to `out0`) and later forwarded to call#6.
- The struct field offsets touched on `ctx` (0x04,0x08,0x0c,0x20,0x24,0x30,0x34,0x38).

**Inferred / GUESS:**
- Semantics of the pointer args (arg2..arg5, arg8, arg9) — labeled as image/params/tables but
  not proven here; they must be confirmed inside the callees.
- That `w`,`h` are *image* width/height (vs. some other 2 dims) — supported by `w*h` → buffer
  size, but inferential.
- `ctx->f20` doubling as both gate flag and a count for #5/#6 — it is read 3× and passed as an
  int to #5/#6; "count" is inferred.

**Open questions (need gdb / callee analysis):**
1. **CALL #4's `r8`** is not explicitly set at the call site — what value does it inherit at
   `0x18000450e`? (Hook #6 above resolves this.)
2. Which callee actually produces the **Q16 similarity transform** that ends up in `sec0_pre`?
