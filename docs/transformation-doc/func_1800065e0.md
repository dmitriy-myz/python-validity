# sub_1800065e0 — read 1 byte (u8) from a byte-stream reader cursor

A tiny serialization primitive: copies **1 byte** out of a stream/buffer object at its
current cursor into a caller-supplied destination, then advances the cursor by 1.
It is the `read_u8` helper of a TLV/blob deserializer (siblings: `sub_1800065b0` = `read_u32`,
`sub_180006610` = `read_n_bytes`). **No transform / geometry math here** — it is plumbing the
matcher's TLV decoder uses to pull bytes out of the `sec0_pre` / pre_v30 stream.

## Signature

```c
// rcx: pointer to a "stream reader" object:
//        +0x08  void*  base       — base pointer of the backing byte buffer
//        +0x10  int32  cursor     — current read offset into the buffer (bytes consumed)
// rdx: void* dst                  — destination address that receives the 1 byte read
// returns: void  (writes through *dst, mutates reader->cursor)
void sub_1800065e0(StreamReader *reader /*rcx*/, void *dst /*rdx*/);
```

Notes / inferred:
- Direction is **read** (stream -> dst). Confirmed via the memcpy at `0x1800031e0`, whose
  ABI is `memcpy(rcx=dst, rdx=src, r8d=count)`. Here the callee receives
  `rcx=dst=(original rdx)` and `rdx=src=(reader->base + reader->cursor)`, so bytes flow
  *from the stream into `*dst`*.
- Caller `sub_180005930` confirms it: right after the call it does
  `movzx r8d, BYTE [rsp+0x22]` and stores that byte into a record — i.e. `[rsp+0x22]`
  was the **out** slot filled by this function. (guess→confirmed)

## Pseudocode

```c
void sub_1800065e0(StreamReader *reader /*rcx*/, void *dst /*rdx*/)
{                                                  // 0x1800065e0  push rbx ; sub rsp,0x20 (shadow space)
    void *out      = dst;                          // 0x1800065e6  mov rax,rdx        (rax = dst)
    int32_t cursor = reader->cursor;               // 0x1800065e9  mov edx,[rcx+0x10] (edx = reader->cursor)
    StreamReader *r = reader;                       // 0x1800065ec  mov rbx,rcx        (save reader for the post-incr)
    void *src = (uint8_t*)reader->base + cursor;    // 0x1800065ef  add rdx,[rcx+0x8]  (src = base + cursor)
    // memcpy(dst=out, src=base+cursor, count=1)
    /* r8d = 1 */                                   // 0x1800065f3  mov r8d,1          (byte count = 1)
    /* rcx = out */                                 // 0x1800065f9  mov rcx,rax        (callee arg0 = dst)
    memcpy_180003.., (rcx=out, rdx=src, r8d=1);     // 0x1800065fc  call 0x1800031e0   (single-byte copy)

    r->cursor += 1;                                 // 0x180006601  add DWORD [rbx+0x10],1   (advance cursor by 1 byte)
                                                    // 0x180006605  add rsp,0x20
                                                    // 0x180006609  pop rbx
    return;                                         // 0x18000660a  ret
}
```

Because the count passed to the memcpy is the immediate `1`, the copy is effectively just
`*(uint8_t*)dst = *(uint8_t*)(base + cursor);` (the memcpy's dword/byte fast paths both
reduce to one byte here — it takes the byte-loop branch at `0x180003240`, copying exactly
1 byte).

## Struct fields & constants

| Access (in this fn)        | Addr        | Meaning                                                        |
|----------------------------|-------------|----------------------------------------------------------------|
| `[rcx+0x8]`  (read)        | 0x1800065ef | `reader->base` — base pointer of the backing byte buffer       |
| `[rcx+0x10]` (read)        | 0x1800065e9 | `reader->cursor` — current read offset (32-bit)                |
| `[rbx+0x10]` (read-modify-write) | 0x180006601 | same `reader->cursor`, incremented by 1 (post-read advance) |
| `rdx` (arg)                | —           | `dst` — destination receiving the 1 byte                       |
| immediate `0x1` in `r8d`   | 0x1800065f3 | memcpy element count = 1 byte (this is the "u8" in `read_u8`)   |
| `sub rsp,0x20`             | 0x1800065e2 | 32-byte shadow space for the `call` (x64 ABI), not a constant   |

No fixed-point, no `0x10000`/`0x8000`, no shifts, no trig. This function holds **no transform math**.

## Callees

- `0x1800031e0` — `memcpy(dst, src, count)`. Aligned dword fast-path loop at `0x180003220`,
  byte-by-byte fallback loop at `0x180003240`; with `count==1` it takes the byte path and
  copies exactly one byte. (Leaf, see disasm; standard memmove/memcpy idiom.)

## GDB verification hooks

To verify a Python re-implementation produces identical reads/cursor advances:

- `break *0x1800065e0` — entry. Dump:
  - `rcx` = reader object pointer; then `*(void**)(rcx+8)` = `reader->base`,
    `*(int*)(rcx+0x10)` = `reader->cursor` (offset about to be read).
  - `rdx` = destination pointer for the byte.
  - Compute expected source byte: `x/1bx (*(unsigned long*)(rcx+8)) + (*(int*)(rcx+0x10))`.
- `break *0x1800065fc` — just before the memcpy. Confirm `rcx`(=dst), `rdx`(=src=base+cursor),
  `r8d`(=1). `x/1bx $rdx` shows the byte that will be read.
- `break *0x180006601` — after the copy, before the cursor bump. `x/1bx $rdx_at_dst`
  (use the saved dst) should now equal the source byte. Read `*(int*)(rbx+0x10)` (pre-incr cursor).
- `break *0x18000660a` — at `ret`. `*(int*)(rbx+0x10)` should be `cursor_before + 1`.
  The byte landed at `*dst` is the value the caller (e.g. `sub_180005930`) will `movzx` next.

Cross-check against the caller `sub_180005930`: e.g. at `0x180005977`
`movzx r8d, BYTE [rsp+0x22]` reads the byte this fn wrote to `[rsp+0x22]` (the `dst` passed
at `0x18000596e`); it is then stored as a record field at `[rax+0x8]`. Matching that store
end-to-end confirms the read order/offsets of the whole TLV decode.

## Confidence & open questions

- **High confidence** on mechanics: this is a 1-byte stream read with a post-read cursor
  increment; `[rcx+0x8]`=base, `[rcx+0x10]`=cursor. The memcpy ABI and the count `1` are
  unambiguous from the disasm.
- **High confidence** on direction (stream→dst = a *reader*), corroborated by caller
  `sub_180005930` consuming the byte immediately after.
- **Inferred (medium)**: field *names* (`base`/`cursor`) and the broader role of the object
  as a "TLV/blob deserializer". Sibling stride sizes back this up: `sub_1800065b0` advances by
  4 (`read_u32`), `sub_180006610` loops advancing by 1 per element (`read_n_bytes`); identical
  `[obj+0x8]+[obj+0x10]` addressing in all three.
- **Open**: this primitive is generic and reused; the *semantic* meaning of each byte read
  belongs to the caller's record layout (see `sub_180005930`, where reads populate counts at
  `+0x8`, and per-entry fields at `+0x14`/`+0x18` of 0x20-stride records). Not relevant to the
  rigid-transform math itself.
