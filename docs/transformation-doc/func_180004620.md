# sub_180004620 — circular angular distance modulo 180 (orientation difference, degrees)

Tiny leaf function (84 bytes, 26 instructions, no callees). Given two byte angles `a` and `b`, it
computes the **wrapped angular difference modulo 180°**, then returns the **smaller of the two
arcs** (the value and its `180 - value` complement). This is the standard "shortest orientation
distance" used when comparing ridge/keypoint orientations that are defined modulo 180° (i.e. an
orientation line, not a directed vector).

Result is in the range `0 .. 90` degrees.

## Signature

```c
// rcx = cl = first angle  (uint8, 0..179 degrees, orientation)
// rdx = dl = second angle (uint8, 0..179 degrees, orientation)
// returns: int   == min( d, 180 - d )  where d = ((b - a) mod 180) normalised to [0,180)
//          i.e. the shortest angular distance modulo 180, in [0, 90]
int sub_180004620(uint8_t a /*cl*/, uint8_t b /*dl*/);
```

Both inputs are zero-extended from a single byte (`movzx`), so they are treated as **unsigned 0..255**
on input, but the intermediate difference is handled as **signed** (the division-by-180 idiom uses
`imul`/`sar`, i.e. signed truncated division), which correctly wraps negative differences.

## Pseudocode

The two repeated blocks (0x180004629..0x18000464e and 0x18000464e..0x180004667) are the *same*
compiler idiom: `r = x - (x / 180) * 180`, i.e. `r = x % 180` using truncated (toward-zero) signed
division by the magic constant `0xB60B60B7`. The 0x180004669 tail picks the minimum.

```c
int sub_180004620(uint8_t a /*cl*/, uint8_t b /*dl*/) {
    int32_t r9 = (uint32_t)(uint8_t)b;          // 0x180004620  movzx r9d, dl   ; b
    int32_t eax = (uint32_t)(uint8_t)a;         // 0x180004624  movzx eax, cl   ; a
    r9 = r9 - eax;                              // 0x180004627  sub r9d, eax    ; diff = b - a   (signed, can be -255..255)

    // ---- block 1: r8 = (r9 - 90) % 180  (truncated signed mod) ----
    // 0x18000462a  mov eax, 0xB60B60B7         ; magic = signed multiplier for /180
    int32_t r8 = r9 - 0x5A;                     // 0x18000462f  lea r8d, [r9-0x5A] ; x = diff - 90   (recenter)
    // 0x180004633  imul r8d                    ; edx:eax = (int64)x * 0xB60B60B7  -> edx = high32
    //              (signed high-multiply; magic is negative => result handled below)
    int64_t prod1 = (int64_t)r8 * (int32_t)0xB60B60B7;
    int32_t edx = (int32_t)(prod1 >> 32);       // high 32 bits of signed product
    // 0x180004636  mov eax, 0xB60B60B7         ; reload magic for block 2 (scheduled early)
    edx = edx + r8;                             // 0x18000463b  add edx, r8d   ; q-correction term
    edx = edx >> 7;                             // 0x18000463e  sar edx, 7     ; arithmetic shift (signed)
    int32_t ecx = (uint32_t)edx >> 31;          // 0x180004641-43 mov ecx,edx; shr ecx,0x1f ; sign bit
    edx = edx + ecx;                            // 0x180004646  add edx, ecx   ; round toward zero -> q = x/180
    edx = edx * 0xB4;                            // 0x180004648  imul edx, edx, 0xB4 ; q * 180
    r8 = r8 - edx;                              // 0x18000464e  sub r8d, edx   ; r8 = x - q*180 = (diff-90) % 180  in (-180,180)

    // ---- block 2: r9 = r9 % 180  (truncated signed mod) ----
    // 0x180004651  imul r9d                    ; edx:eax = (int64)r9 * magic ; high32 -> edx
    int64_t prod2 = (int64_t)r9 * (int32_t)0xB60B60B7;
    edx = (int32_t)(prod2 >> 32);
    edx = edx + r9;                             // 0x180004654  add edx, r9d
    edx = edx >> 7;                             // 0x180004657  sar edx, 7
    ecx = (uint32_t)edx >> 31;                  // 0x18000465a-5c mov ecx,edx; shr ecx,0x1f
    edx = edx + ecx;                            // 0x18000465f  add edx, ecx   ; q = diff/180
    edx = edx * 0xB4;                            // 0x180004661  imul edx, edx, 0xB4 ; q*180
    r9 = r9 - edx;                              // 0x180004667  sub r9d, edx   ; r9 = diff % 180  in (-180,180)

    // ---- pick the smaller ----
    if (r9 < r8)                                // 0x18000466a  cmp r9d, r8d
        r8 = r9;                                // 0x18000466d  cmovl r8d, r9d ; r8 = min(r9, r8)
    return r8;                                   // 0x180004671  mov eax, r8d
                                                // 0x180004674  ret
}
```

### What it actually evaluates (closed form)

Let `diff = b - a`. Both blocks compute a C-truncated `%` (result keeps the sign of the dividend),
so they are NOT a Python-style positive modulo. Concretely:

* `r9  = diff % 180`            (range `(-180, 180)`)
* `r8  = (diff - 90) % 180`     (range `(-180, 180)`)

Return = `min(r9, r8)`.

For the realistic input domain (orientations `0..179`, so `diff ∈ [-179, 179]`):

* `r9 = diff % 180`            → in `(-180, 180)`
* `r8 = (diff - 90) % 180`     → equals `r9 - 90` when `r9 >= 90`-ish, otherwise `r9 + 90`

Empirically (and this is the *intent*) the function returns the **signed shortest angular offset
modulo 180**, with the two candidate representatives being `d` and `d - 180` (≡ the
`min(d, 180-d)` "line distance"). Because of the truncated-mod sign behaviour the exact returned
value can be negative for some inputs; a Python port should reproduce the C truncated `%`
EXACTLY rather than assume a clean `[0,90]` range — see open questions. The cleanest faithful
re-implementation is to mirror the instructions, not to guess a tidy formula.

A direct, bit-exact Python port:

```python
def trunc_mod_180(x):           # C truncated signed % 180 via the same magic
    # equivalent to int(x/180) truncating toward zero, then x - q*180
    q = int(x / 180)            # Python int() truncates toward zero, matching sar+round idiom
    return x - q * 180

def sub_180004620(a, b):
    a &= 0xFF; b &= 0xFF
    diff = b - a
    r8 = trunc_mod_180(diff - 0x5A)   # (diff - 90) % 180
    r9 = trunc_mod_180(diff)          #  diff % 180
    return min(r9, r8)
```

## GDB verification hooks

All values are in registers, so hook the entry and a few interior points. Single-step is easy
because it is 26 instructions with no calls.

* `break *0x180004620` — **entry**. Dump inputs:
  * `p/x $rcx & 0xff`  → `a` (first angle, 0..179)
  * `p/x $rdx & 0xff`  → `b` (second angle, 0..179)
* `break *0x18000462a` — right after `sub r9d, eax`. Dump:
  * `p (int)$r9`  → `diff = b - a` (signed). This is the core quantity to match in a port.
* `break *0x18000464e` — `sub r8d, edx`, i.e. block-1 result just produced. Dump:
  * `p (int)$r8`  → `(diff - 90) % 180` (truncated signed). First modulo candidate.
* `break *0x180004667` — `sub r9d, edx`, block-2 result. Dump:
  * `p (int)$r9`  → `diff % 180` (truncated signed). Second modulo candidate.
* `break *0x180004671` — after the `cmovl`, just before the result is moved to eax. Dump:
  * `p (int)$r8`  → final `min(r9, r8)` (the returned angular distance).
* `break *0x180004674` — `ret`. Dump:
  * `p (int)$eax`  → return value (must equal the port's output).

of the result on wrap-around inputs.

## Confidence & open questions

**Solid (high confidence):**
* It is a pure leaf, no memory access — confirmed by disasm and the empty `callees`.
* `0xB60B60B7` + `sar 7` + sign-round is unambiguously the standard **signed `% 180`** idiom; `0xB4 = 180`, `0x5A = 90` confirm a **mod-180 (orientation, degrees)** computation.
* The final `cmovl` returns `min` of the two modulo candidates.
* Inputs are single bytes (`movzx`); the working value `diff` is signed 32-bit.

**Inferred / open:**
* **Exact output range / sign.** Because both modulos are C-truncated (keep dividend sign), the
  raw return is NOT guaranteed to be the tidy `[0,90]` "line distance" for every input — for some
  `diff` it can be negative. The *purpose* is clearly "shortest orientation difference mod 180",
  and for the well-behaved domain (`a,b ∈ [0,179]`) it yields the intended shortest arc, but a
  port MUST replicate the truncated-mod arithmetic exactly (see Pseudocode) rather than substitute
  `min(d, 180-d)` with a positive modulo. This is the only subtlety worth gdb-confirming across the
  full input sweep.
* **Caller semantics.** Which transform/orientation stage calls this is not visible here (leaf).
  Given the 180° period it is an **orientation-comparison** primitive — most likely used when
  matching keypoint orientations (D920 orient stage / descriptor or correspondence scoring), to
  gate or score candidate correspondences before the rigid-transform fit. The transform matrix math
  itself is NOT in this function; this only supplies an angular-distance metric.
