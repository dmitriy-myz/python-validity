# sub_180007450 — Q16 rigid/similarity transform of a 2D point (thin wrapper)

`sub_180007450` is a tiny (32-byte, 9-instruction) **argument-shuffling wrapper** around the
real worker `sub_180006bc0`. It takes a destination `Point*`, a source `Point*`, and a Q16
similarity-transform parameter block, unpacks the source point's two `int32` coordinates, and
tail-calls the worker. The worker applies the classic fixed-point rigid transform

```
out_x = (a*X - b*Y + tx + 0x8000) >> 16
out_y = (b*X + a*Y + ty + 0x8000) >> 16
```

i.e. `R = [[a, -b], [b, a]]`, `t = (tx, ty)`, all in Q16 (16.16) fixed point with `+0x8000`
round-to-nearest before the arithmetic `>>16`. This is precisely the per-point application of a
`sec0_pre`-style inter-frame similarity transform.

> NOTE: the actual matrix/round/shift math lives in the callee `sub_180006bc0`; this wrapper only
> marshals arguments. The callee disasm was read and is documented below so the wrapper's contract
> is unambiguous.

---

## Signature

```c
// Q16 (16.16 fixed point) similarity transform parameter block.
typedef struct {
    int32_t a;    // +0x00  cos*65536  (R[0][0] = R[1][1])
    int32_t b;    // +0x04  sin*65536  (R[1][0] = -R[0][1])
    int32_t tx;   // +0x08  translation x, already in Q16 (pre-shifted by 16)
    int32_t ty;   // +0x0c  translation y, already in Q16
} Q16Transform;

typedef struct {
    int32_t x;    // +0x00
    int32_t y;    // +0x04
} Point2i;        // plain integer coordinates (NOT Q16)

// rcx = out, rdx = in, r8 = M
void sub_180007450(Point2i *out, const Point2i *in, const Q16Transform *M);
```

Argument roles (Windows x64):
- `rcx` — **out** : destination point. Worker writes `out->x` at `[rcx+0x0]`, `out->y` at `[rcx+0x4]`.
- `rdx` — **in**  : source point. Read `in->x = *(int32*)(rdx+0x0)`, `in->y = *(int32*)(rdx+0x4)`.
- `r8`  — **M**   : pointer to the 4×`int32` Q16 transform `{a, b, tx, ty}`.

Returns: void (worker returns void; wrapper ignores eax).

## Pseudocode

### Wrapper `sub_180007450` (0x180007450 – 0x180007470)

```c
void sub_180007450(Point2i *rcx_out, const Point2i *rdx_in, const Q16Transform *r8_M)
{
    // 0x180007450: sub rsp,0x38                  ; reserve shadow + 1 stack arg slot
    // 0x180007454: mov rax,rdx                   ; rax = in
    // 0x180007457: mov [rsp+0x20],r8             ; stash M -> becomes callee's [rsp+0x28] (5th arg)
    // 0x18000745c: lea rdx,[rcx+0x4]             ; arg2 = &out->y   (rcx+4)
    // 0x180007460: mov r9d, [rax+0x4]            ; arg4 = in->y
    // 0x180007464: mov r8d, [rax+0x0]            ; arg3 = in->x
    //   (rcx unchanged -> arg1 = &out->x)
    // 0x180007467: call 0x180006bc0              ; transform_point_q16(&out->x, &out->y, in->x, in->y, M)
    sub_180006bc0(/*rcx*/ &rcx_out->x,
                  /*rdx*/ &rcx_out->y,
                  /*r8d*/ rdx_in->x,
                  /*r9d*/ rdx_in->y,
                  /*[rsp+0x28]*/ r8_M);
    // 0x18000746c: add rsp,0x38
    // 0x180007470: ret
}
```

So the wrapper exposes a `(out_ptr, in_ptr, M)` interface and lowers it to the worker's
`(out_x_ptr, out_y_ptr, x_val, y_val, M)` interface.

### Worker `sub_180006bc0` (0x180006bc0 – 0x180006c3c) — the actual transform math

Args as received: `rcx = out_x_ptr`, `rdx = out_y_ptr`, `r8d = X` (in.x), `r9d = Y` (in.y),
`[rsp+0x28] = M` (matrix ptr, loaded into r11).

```c
void sub_180006bc0(int32_t *out_x, int32_t *out_y, int32_t X, int32_t Y, const Q16Transform *M)
{
    // 0x180006bc0..0x180006bcf: save rbx,rbp,rsi,rdi to shadow space (prologue)
    // 0x180006bd4: r11 = M                        ; [rsp+0x28]
    // 0x180006bd9: esi = r9d  = Y
    // 0x180006bdc: edi = r8d  = X
    // 0x180006bdf: ebx  = M->a       (*(r11+0x00))
    // 0x180006be2: r9d  = M->b       (*(r11+0x04))
    // 0x180006be6: rbp  = rdx        = out_y_ptr
    // 0x180006be9: edx  = M->ty      (*(r11+0x0c))
    // 0x180006bed: r10d = ebx        = a
    // 0x180006bf0: eax  = r9d        = b
    // 0x180006bf3: imul ebx,  esi    ; ebx  = a * Y
    // 0x180006bf6: imul r9d,  edi    ; r9d  = b * X
    // 0x180006bff: imul eax,  esi    ; eax  = b * Y
    // 0x180006c07: imul r10d, r8d    ; r10d = a * X
    // 0x180006c0b: sub  r10d, eax    ; r10d = a*X - b*Y
    // 0x180006c0e: eax  = M->tx      (*(r11+0x08))
    // 0x180006c12: r8d  = r10d + tx + 0x8000   ; lea r8d,[r10+rax+0x8000]
    // 0x180006c1a: eax  = edx + r9d  = ty + b*X        ; lea eax,[rdx+r9]
    // 0x180006c1e: sar  r8d, 0x10    ; (a*X - b*Y + tx + 0x8000) >> 16   (signed)
    // 0x180006c22: *out_x = r8d
    // 0x180006c25: ecx  = ebx + eax + 0x8000 = a*Y + (ty + b*X) + 0x8000 ; lea ecx,[rbx+rax+0x8000]
    // 0x180006c31: sar  ecx, 0x10    ; (b*X + a*Y + ty + 0x8000) >> 16   (signed)
    // 0x180006c34: *out_y = ecx      ; [rbp+0]
    // 0x180006c2c/0x180006c37: restore rbx,rbp
    // 0x180006c3c: ret

    *out_x = (int32_t)(((int64_t? no — 32-bit) M->a*X - M->b*Y + M->tx + 0x8000) >> 16);
    *out_y = (int32_t)((            M->b*X + M->a*Y + M->ty + 0x8000) >> 16);
}
```

> Signedness/width: all `imul` are 32-bit (`imul r32, r32`), so the products and sums are computed
> in **32-bit two's complement (overflow wraps mod 2^32)**, and `sar` is an **arithmetic (signed)**
> shift. A faithful Python port must emulate 32-bit wraparound on the products/sums before the
> arithmetic `>>16`. The `+0x8000` is round-to-nearest for the Q16→int truncation.

## GDB verification hooks

Goal: confirm a Python re-implementation produces byte-identical outputs.

1. **`break *0x180007460`** (wrapper, just before the inputs are loaded; matrix already stashed)
   - `x/2wd $rcx`  → not yet written (this is the out struct addr; record `$rcx` = out_ptr).
   - `x/2wd $rdx`  → **input point** `[in.x, in.y]` (rdx still = original `in` here; `rax`=`rdx`).
   - `x/4wd $r8`   → **matrix M** `[a, b, tx, ty]` (r8 still holds the original 3rd arg).
   Record `(in.x, in.y, a, b, tx, ty)` — these are the full inputs to one transform.

2. **`break *0x180006bd4`** (worker entry, after r11 loaded) — re-confirm matrix:
   - `x/4wd $r11`  → `[a, b, tx, ty]`.
   - `p/d $r8d` , `p/d $r9d`  → `X`, `Y` (the input coords).

3. **`break *0x180006c1e`** (right where `sar r8d,0x10` is about to run) — pre-shift X accumulator:
   - `p/d $r8d` → `(a*X - b*Y + tx + 0x8000)` **before** the shift. Verify your Python intermediate
     (in 32-bit wrap) matches exactly. Step one instr, then `p/d $r8d` → final `out_x`.

4. **`break *0x180006c22`** (just executed `mov [rcx],r8d`) — captured `out_x`:
   - `x/1wd $rcx` → written `out_x`.

5. **`break *0x180006c31`** (about to `sar ecx,0x10`) — pre-shift Y accumulator:
   - `p/d $ecx` → `(b*X + a*Y + ty + 0x8000)` before shift. Step, `p/d $ecx` → final `out_y`.

6. **`break *0x180006c34`** (just executed `mov [rbp],ecx`) — captured `out_y`:
   - `x/1wd $rbp` → written `out_y`. Combined with hook 4 you have the full `(out_x,out_y)`.

Suggested oneshot dump at the worker exit `break *0x180006c3c`:
`p/d $r8d`-style won't survive epilogue; instead read the destinations:
`x/1wd <out_x_ptr>` and `x/1wd <out_y_ptr>` (the addresses captured at hook 1's `$rcx` and `$rcx+4`).

## Confidence & open questions

**Solid (high confidence):**
- The wrapper's argument lowering: `(out_ptr=rcx, in_ptr=rdx, M=r8)` → worker
  `(&out.x, &out.y, in.x, in.y, M)`. Directly from the 9 instructions.
- The worker math: `out_x=(a*X−b*Y+tx+0x8000)>>16`, `out_y=(b*X+a*Y+ty+0x8000)>>16`, with the
  `R=[[a,-b],[b,a]]` Q16 structure, `+0x8000` rounding, signed `>>16`. Directly from the disasm of
  `sub_180006bc0`.
- Matrix layout `{a@0, b@4, tx@8, ty@0xc}` and Point2i `{x@0, y@4}`.

**Inferred / lower confidence:**
- The names `a`/`b` = `cos·65536`/`sin·65536` are the conventional interpretation of a Q16
  `[[a,-b],[b,a]]` block; this matches the project's documented sec0_pre transforms but the trig
  origin is not visible in this function — it would be set by whatever populates M.
- `tx`/`ty` being already in Q16: inferred from the fact they are added *before* the `>>16` (so
  they must already carry the ·65536 scale). Confirm against the producer of M.
- 32-bit wraparound semantics: the disasm uses 32-bit `imul`/`lea`, so products and sums are
  modulo 2^32. For typical coordinate ranges (image < ~512 px) with Q16 `a,b ≤ 65536` this won't
  overflow, but a strict port should still mask to 32-bit signed before shifting to be byte-exact.

**Open questions:**
- Whether callers ever pass the same pointer for `in` and `out` (in-place transform) — the worker
  reads both inputs (into rsi/rdi) before any store, so in-place is safe regardless.
- Identity of the producer of `M` (where `a,b,tx,ty` come from) — out of scope for this leaf/wrapper.
