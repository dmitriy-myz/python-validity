# sub_180003320 — clone a 6-qword "buffered-stream / range view" struct and re-anchor one of its two sub-ranges via the sub_1800032c0 slice builder

This is a **container / range-view manipulation** helper, **not** transform/geometry math.
It copies a 48-byte (0x30) descriptor from `src` into `dst` verbatim, then — depending on
whether a position `pos` (arg3) falls inside the "committed" range or past it — rebuilds **one
of two embedded 0x18-byte sub-views** by calling the slice constructor `sub_1800032c0` and
writes the resulting `(count, base_ptr, end_ptr)` triple back into either the **second**
sub-view (offsets +0x18/+0x20/+0x28 of `dst`) or the **first** sub-view (offsets +0/+0x8/+0x10
of `dst`).

The shape is exactly that of a C++ stream/iterator pair such as
`std::basic_streambuf`'s get/put areas, or a custom "two-cursor buffer" (a get area at +0 and a
put/overflow area at +0x18). The thing being sliced is a raw `char*`/`uint8_t*` buffer, aligned
**up to the next multiple of 8** (`+7 & ~7`), so the payload is a byte buffer, not floats.

## Signature

```c
// All structs are 48 bytes (0x30): two parallel 24-byte (0x18) sub-views.
// view0 = { int32 count@+0; void* base@+0x8; void* end@+0x10 }
// view1 = { int32 count@+0x18; void* base@+0x20; void* end@+0x28 }
typedef struct StreamView {   // 0x30 bytes
    int32_t  v0_count;        // +0x00  committed/used length of region 0
    /* pad +0x04 */
    uint8_t* v0_base;         // +0x08  region-0 buffer base
    uint8_t* v0_end;          // +0x10  region-0 buffer end (one-past / cursor)
    int32_t  v1_count;        // +0x18  committed/used length of region 1
    /* pad +0x1c */
    uint8_t* v1_base;         // +0x20  region-1 buffer base
    uint8_t* v1_end;          // +0x28  region-1 buffer end
} StreamView;

// sub_1800032c0 fills a 0x30-byte "Slice" result describing aligned sub-range.
//   Slice { int32 count@+0; void* base@+0x8; void* alignedEnd@+0x10; ...; void* a@+0x18; void* b@+0x20; void* c@+0x28 }
StreamView* sub_180003320(
    StreamView* dst,   // rcx  — output, returned in rax
    StreamView* src,   // rdx  — source descriptor (copied wholesale)
    int32_t     pos,   // r8d  — a position/length to re-base the active region at (signed)
    uint8_t*    buf);  // r9   — buffer base pointer handed to the slice builder
```

Return value: `dst` (rax = rbx).

## Pseudocode

```c
StreamView* sub_180003320(StreamView* dst /*rcx*/, StreamView* src /*rdx*/,
                          int32_t pos /*r8d*/, uint8_t* buf /*r9*/)
{
    // ---- prologue / wholesale 0x30-byte struct copy src -> dst ----   // 0x180003320
    // rex push rbx ; sub rsp,0x90
    r10 = buf;                                  // 0x18000332c  (r9 saved into r10)
    rbx = dst;                                  // 0x18000332f
    *(u64*)(dst+0x00) = *(u64*)(src+0x00);      // 0x180003329 / 0x180003332
    *(u64*)(dst+0x08) = *(u64*)(src+0x08);      // 0x180003335 / 0x180003339
    *(u64*)(dst+0x10) = *(u64*)(src+0x10);      // 0x18000333d / 0x180003341
    *(u64*)(dst+0x18) = *(u64*)(src+0x18);      // 0x180003345 / 0x180003349
    *(u64*)(dst+0x20) = *(u64*)(src+0x20);      // 0x18000334d / 0x180003351
    u64 r9v = *(u64*)(src+0x28);                // 0x180003355   (v1_end)
    *(u64*)(dst+0x28) = r9v;                    // 0x18000335c
    // r9 = r9v
    if (r9v == 0)                               // 0x180003359 test rax,rax / 0x180003363 je
        goto L_anchor_view0;                    //   -> 0x1800033df

    int32_t eax = *(i32*)(src+0x18);            // 0x180003365  (v1_count)
    if (pos > eax)                              // 0x180003368 cmp r8d,eax / 0x18000336b jg (signed)
        goto L_anchor_view0;                    //   -> 0x1800033df

    // ====== PATH A : pos is within view1's committed range -> re-anchor VIEW1 ======   // 0x18000336d
    // Build args for sub_1800032c0:
    //   rcx = &slice@[rsp+0x60]   (out)
    //   rdx = buf                 (r10)            <-- note: rdx receives the buffer base
    //   r8d = pos
    //   r9  = src+? (carried)  -- actually r9 still holds v1_end (*(src+0x28))
    //   [rsp+0x28] = eax = v1_count           // 0x18000336d
    //   [rsp+0x20] = *(u64*)(src+0x20) = v1_base   // 0x180003371 / 0x18000337d
    Slice* res = sub_1800032c0(
                     /*rcx*/ &slice /*[rsp+0x60]*/,   // 0x180003375
                     /*rdx*/ buf,                      // 0x18000337a  (r10)
                     /*r8d*/ pos,
                     /*r9 */ r9v /*v1_end*/,
                     /*[rsp+0x20]*/ v1_base,
                     /*[rsp+0x28]*/ v1_count);         // call 0x180003382

    // copy the 0x30-byte Slice result into a stack scratch at [rsp+0x30]   // 0x180003387..0x1800033b6
    scratch[0x00..0x30] = res[0x00..0x30];   // 6 qwords, plain memcpy idiom

    // write the active triple back into dst.VIEW1 (offsets +0x18/+0x20/+0x28)
    *(u64*)(dst+0x20) = scratch[+0x08];      // 0x1800033ba / 0x1800033bf   v1_base  <- Slice.base
    *(u64*)(dst+0x28) = scratch[+0x10];      // 0x1800033c3 / 0x1800033c8   v1_end   <- Slice.alignedEnd
    *(i32*)(dst+0x18) = scratch[+0x00];      // 0x1800033cc / 0x1800033d0   v1_count <- Slice.count
    return dst;                              // 0x1800033d3 mov rax,rbx
    // add rsp,0x90 ; pop rbx ; ret          // 0x1800033d6 .. 0x1800033de

L_anchor_view0:                               // 0x1800033df
    // ====== PATH B : view1 empty OR pos past v1_count -> re-anchor VIEW0 ======
    int32_t v0_count = *(i32*)(src+0x00);     // 0x1800033df
    u64     v0_end   = *(u64*)(src+0x10);     // 0x1800033e1   (loaded into r9)
    //   [rsp+0x28] = v0_count                 // 0x1800033ea
    //   [rsp+0x20] = *(u64*)(src+0x08) = v0_base   // 0x1800033ee / 0x1800033f5
    Slice* res = sub_1800032c0(
                     /*rcx*/ &slice /*[rsp+0x60]*/,   // 0x1800033e5
                     /*rdx*/ buf,                      // 0x1800033f2  (r10)
                     /*r8d*/ pos,                       // (pos unchanged from caller)
                     /*r9 */ v0_end,
                     /*[rsp+0x20]*/ v0_base,
                     /*[rsp+0x28]*/ v0_count);          // call 0x1800033fa

    scratch[0x00..0x30] = res[0x00..0x30];   // 0x1800033ff..0x18000342e  (6 qwords)

    // write the active triple back into dst.VIEW0 (offsets +0/+0x8/+0x10)
    *(u64*)(dst+0x08) = scratch[+0x08];      // 0x180003432 / 0x180003437   v0_base  <- Slice.base
    *(u64*)(dst+0x10) = scratch[+0x10];      // 0x18000343b / 0x180003440   v0_end   <- Slice.alignedEnd
    *(i32*)(dst+0x00) = scratch[+0x00];      // 0x180003444 / 0x180003448   v0_count <- Slice.count
    return dst;                              // 0x18000344a mov rax,rbx
    // add rsp,0x90 ; pop rbx ; ret          // 0x18000344d .. 0x180003455
}
```

### The slice builder it calls — sub_1800032c0 (for porting)

```c
// out is 0x30 bytes. Inputs: rcx=out, rdx=&outBase?, r8d=pos, r9=bufEnd,
//                            [rsp+0x20]=base, [rsp+0x30]=count(=r11d)
Slice* sub_1800032c0(Slice* out /*rcx -> r10*/, void** pBase /*rdx*/,
                     int32_t pos /*r8d*/, uint8_t* bufEnd /*r9*/ /*=end ptr*/)
{
    void*  base  = arg[rsp+0x28];      // 0x1800032c0  (the v?_base passed by caller)
    int32_t cnt  = arg[rsp+0x30];      // 0x1800032c5  (r11d = the v?_count)
    out[+0x08] = base;                 // 0x1800032cd
    out[+0x00] = 0;                    // 0x1800032d8  count = 0  (default / "empty")
    out[+0x10] = 0;                    // 0x1800032db
    out[+0x18] = 0;                    // 0x1800032df
    out[+0x20] = 0;                    // 0x1800032e3
    out[+0x28] = 0;                    // 0x1800032e7
    if (pos > cnt)                     // 0x1800032d5 cmp r8d,r11d / 0x1800032eb jg (signed)
        return out;                    // 0x18000330d  -> empty slice

    int64_t p = (int64_t)pos;          // 0x1800032ed movsxd  (SIGNED)
    *pBase = bufEnd;                   // 0x1800032f0  (*rdx = r9)
    p += (int64_t)bufEnd;              // 0x1800032f3  rcx = pos + bufEnd
    uint64_t aligned = (p + 7) & ~7;   // 0x1800032f6 / 0x1800032fa  round UP to mult of 8
    out[+0x10] = aligned;              // 0x180003300  alignedEnd
    int32_t rem = (int32_t)(p - aligned);  // 0x1800032fe sub ecx,eax (low 32 bits)
    rem = rem - pos + cnt;             // 0x180003304 / 0x180003307   = cnt - (aligned - bufEnd)
    out[+0x00] = rem;                  // 0x18000330a  new count
    return out;                        // 0x18000330d
}
```

Net effect of the slice math: given a buffer end pointer `bufEnd`, a signed offset `pos`, and a
remaining `count`, it advances the end pointer by `pos`, rounds that address **up to an 8-byte
boundary**, stores it as the new aligned cursor (`+0x10`), and recomputes the remaining byte
count as `count - (aligned_cursor - bufEnd)` (i.e. `count - pos - alignment_padding`). It is a
classic **8-byte-aligned buffer-advance / put-area reset**.

Constants:

| Const | Where | Meaning |
|---|---|---|
| `0x90` | prologue/epilogue | local frame size (only ~0x60 used) |
| `0x30` (six qwords) | both paths | struct/Slice copy size = 48 bytes |
| `+0x7` , `0xFFFFFFFFFFFFFFF8` (`~7`) | sub_1800032c0 @0x1800032f6/0x1800032fa | **round-up to 8-byte alignment** |

No fixed-point (>>16, *65536, 0x10000, 0x8000), no trig, no matrix, no sort/voting. The only
arithmetic is pointer alignment and a count adjustment on byte buffers.

## Callees

- `0x1800032c0` — slice/range builder: advance a buffer-end pointer by a signed `pos`, round
  the result up to an 8-byte boundary, and recompute the remaining count. Returns a 0x30-byte
  `Slice {count@+0, base@+0x8, alignedEnd@+0x10, ...}`. (Decompiled inline above; if a separate
  file exists see `func_1800032c0.md`.)

## GDB verification hooks

To verify a Python re-implementation produces identical intermediate values:

- `break *0x180003359` — entry decision. Dump `[rdx+0x28]` (v1_end). If 0 → PATH B.
  Also dump the full copied struct at `rcx`: `x/6gx $rcx`.
- `break *0x18000336b` — the signed gate. Dump `r8d` (pos) and `eax` (= `[rdx+0x18]` = v1_count).
  Branch taken (PATH B) iff `(int32)pos > (int32)v1_count`.
- `break *0x180003382` — PATH A call into sub_1800032c0. Dump:
  - `rdx` = buf base, `r8d` = pos, `r9` = v1_end,
  - `[rsp+0x20]` = v1_base, `[rsp+0x28]` = v1_count (`x/2gx $rsp+0x20`).
- `break *0x1800033fa` — PATH B call into sub_1800032c0. Dump the same: `rdx`(buf), `r8d`(pos),
  `r9`(v0_end), `[rsp+0x20]`(v0_base), `[rsp+0x28]`(v0_count).
- **Inside the slice builder** `break *0x180003300` — dump `rax` = the 8-byte-aligned cursor
  (`alignedEnd`, written to `out+0x10`). `break *0x18000330a` — dump `ecx` = the recomputed
  remaining `count` (written to `out+0x00`). These two are the only non-trivial computed values.
- `break *0x1800033ba` (PATH A) / `break *0x180003432` (PATH B) — just before write-back.
  Dump the scratch `Slice` at `x/6gx $rsp+0x30`; then after the function returns dump the final
  `dst` with `x/6gx <dst>` to confirm `(count,base,end)` landed in the right sub-view
  (+0x18/+0x20/+0x28 for A, +0/+0x8/+0x10 for B).

For a byte-exact port, the only equations to match are the two lines in `sub_1800032c0`:
`alignedEnd = (bufEnd + pos + 7) & ~7` and `count' = count - (alignedEnd - bufEnd)` — both
exercised under the `pos <= count` guard.

## Confidence & open questions

- **Solid (high):** the control flow, the wholesale 0x30-byte copy, the two write-back targets
  (view1 vs view0), the null-check on `v1_end` selecting the path, and the signed `pos>count`
  gate. The slice arithmetic in `sub_1800032c0` (advance + round-up-to-8 + count fixup) is fully
  transcribed and unambiguous.
- **Definite (high):** this routine performs **no** transform/geometry/fixed-point math. It is a
  buffer/stream range-view manager. `is_transform_math = false`. It is reachable from the
  template/geometry call tree (callers 0x180003880, 0x1800043d0, 0x1800046e0) only as a generic
  serialization/buffer plumbing primitive — likely the put/get-area reset of a custom byte stream
  used while *serializing* sec0_pre, not while computing the transforms themselves.
- **Inferred (medium):** field names (`v0_*`/`v1_*`, "get/put area"). The two sub-views are
  symmetric 24-byte `{count, base, end}` triples; whether view0 is "read" and view1 is "write"
  (streambuf convention) vs the reverse is a naming guess. The `Slice` member layout beyond
  `{count@0, base@8, alignedEnd@0x10}` is only partially used here (members at +0x18/+0x20/+0x28
  are copied through but originate as 0 from the builder when the empty-branch is not taken — they
  are written 0 by the builder and copied verbatim).
- **Open:** what `pos` semantically represents in the caller (a sequence position / number of
  bytes already produced?) and whether `pBase` (`rdx` in the builder, here `buf`) is an out-param
  the caller reads afterward. Resolve via the caller hooks above (esp. 0x180003880).
