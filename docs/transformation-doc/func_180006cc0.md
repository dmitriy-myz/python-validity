# sub_180006cc0 — rigid 2D similarity-transform composition (B ∘ A), with rotation renormalization

This function **composes two rigid 2D similarity transforms in Q16 fixed-point**
and writes the result to an output transform. Both inputs and the output use the
4-int32 layout that `sec0_pre` records use:

```
struct Xform { int32 a;   // +0x0  R[0][0] =  cos·65536   (and R[1][1])
               int32 b;   // +0x4  R[1][0] =  sin·65536   (so R[0][1] = -b)
               int32 tx;  // +0x8  translation x (Q16, integer-ish — see note)
               int32 ty;  // +0xc  translation y (Q16) }
```

The math performed is the standard composition of two affine maps
`X(p) = R·p + t`:

```
out = B ∘ A      (apply A first, then B)
  R_out = R_B · R_A         -> stored as (a_out, b_out)
  t_out = t_B + R_B · t_A   -> stored as (tx_out, ty_out)
```

with `R = [[a, -b], [b, a]]` (a = cos·65536, b = sin·65536). After computing the
four output fields, the function **tail-calls `sub_180006c40`** to renormalize the
composed rotation pair `(out.a, out.b)` back onto the unit circle (Q16), removing
the magnitude drift that integer multiplication of two unit rotations introduces.

> Naming convention used below: `rdx` = transform **A** (the "right"/first-applied
> operand; also the one whose `tx,ty` get rotated), `r8` = transform **B** (the
> "left"/second-applied operand whose translation is added last). This pairing is
> dictated by the math, not by the register names — see "Confidence" for which is
> truly which.

## Signature

```c
// Composes two rigid Q16 similarity transforms: *out = B ∘ A.
// Then tail-calls sub_180006c40(out, out+1) to renormalize (out.a, out.b)
// to a Q16 unit vector. No meaningful return value (control flow is a tail jmp).
//
//   rcx = out -> Xform*  : OUTPUT transform (4× int32: a, b, tx, ty)
//   rdx = A   -> Xform*  : first-applied transform  (its t is rotated by R_B)   [GUESS of role]
//   r8  = B   -> Xform*  : second-applied transform (its t is added last)        [GUESS of role]
//
// All Xform fields are signed int32 (movsxd-free; all shifts are arithmetic `sar`).
void sub_180006cc0(Xform *out /*rcx*/, const Xform *A /*rdx*/, const Xform *B /*r8*/);
```

Field aliases used in the pseudocode (matching the struct above):
`A = {a0=A.a, a1=A.b, a2=A.tx, a3=A.ty}`, `B = {b0=B.a, b1=B.b, b2=B.tx, b3=B.ty}`.
**Note:** the disasm reads the *rotation* operands from `rdx` (=B-by-register-name)
and the *translation-being-rotated* operands from `r8`. I keep the disasm's actual
register reads literal in the pseudocode and call them `A`/`B` per math role.

## Pseudocode

```c
void sub_180006cc0(int *out /*rcx*/, const int *RDX /*rdx*/, const int *R8 /*r8*/)
{
    // ---- prologue ----
    //   mov [rsp+0x8], rbx ; push rdi ; sub rsp,0x20            0x180006cc0/cc5/cc6

    // cache pointers (registers get reused below)
    //   rbx = rdx (RDX operand) ; rdi = rcx (out) ; r11 = r8 (R8 operand)
    //                                                            0x180006cd6/cd9/cdc

    // ========================================================================
    // BLOCK 1 — out[0] = rotation a_out = (RDX.a * R8.a - RDX.b * R8.b) >> 16
    //           (computed as ((RDX.a>>1)*(R8.a>>1) - (RDX.b>>1)*(R8.b>>1) + 0x2000) >> 14)
    // ========================================================================
    int r10 = RDX[0] >> 1;                   // r10d = *(rdx)   >>1   0x180006cca, 0x180006cdf
    int r9  = RDX[1] >> 1;                   // r9d  = *(rdx+4) >>1   0x180006ccd, 0x180006ce2
    int t   = R8[0]  >> 1;                   // eax  = *(r8)    >>1   0x180006cd1, 0x180006cd4
    r10 = r10 * t;                           // r10d *= eax           0x180006ce5
    t   = R8[1] >> 1;                        // eax = *(r8+4) >>1     0x180006ce9, 0x180006ced
    r9  = r9 * t;                            // r9d *= eax            0x180006cef
    r10 = r10 - r9;                          // r10d -= r9d           0x180006cf3
    r10 = r10 + 0x2000;                      // += 0x2000 (round)     0x180006cf6
    r10 = r10 >> 0xe;                        // sar 14 (signed)       0x180006cfd
    out[0] = r10;                            // *(rcx) = a_out        0x180006d01

    // ========================================================================
    // BLOCK 2 — out[1] = rotation b_out = (RDX.a * R8.b + RDX.b * R8.a) >> 16
    //           (((RDX.a>>1)*(R8.b>>1) + (RDX.b>>1)*(R8.a>>1) + 0x2000) >> 14)
    // ========================================================================
    int d = RDX[0] >> 1;                     // edx = *(rdx)   >>1    0x180006d04, 0x180006d0d
    int c = R8[0]  >> 1;                     // ecx = *(r8)    >>1    0x180006d06, 0x180006d0f
    t     = R8[1]  >> 1;                     // eax = *(r8+4)  >>1    0x180006d09, 0x180006d11
    d = d * t;                               // edx = (RDX.a>>1)*(R8.b>>1)   0x180006d13
    t = RDX[1] >> 1;                         // eax = *(rbx+4) >>1    0x180006d16, 0x180006d19
    c = c * t;                               // ecx = (R8.a>>1)*(RDX.b>>1)   0x180006d1b
    int e = (d + c + 0x2000) >> 0xe;         // lea+sar 14            0x180006d1e, 0x180006d25
    out[1] = e;                              // *(rcx+4) = b_out      0x180006d28

    // ========================================================================
    // BLOCK 3 — out[2] = tx_out = R8.tx + (RDX.a * R8.tx? ... ) ...
    //           ACTUAL:  out[2] = ((R8.tx>>8)*(RDX.a>>2) - (R8.ty>>8)*(RDX.b>>2)) >> 6
    //                              + RDX.tx
    //   i.e. tx_out = RDX.tx + ( RDX.a*R8.tx - RDX.b*R8.ty ) >> 16
    //   = (t_RDX + R_RDX · t_R8).x        [rotate R8's translation by RDX's rotation]
    // ========================================================================
    d = R8[2] >> 8;                          // edx = *(r8+8)  >>8    0x180006d2b, 0x180006d35
    c = R8[3] >> 8;                          // ecx = *(r8+0xc)>>8    0x180006d2f, 0x180006d38
    t = RDX[0] >> 2;                         // eax = *(rbx)   >>2    0x180006d33, 0x180006d3b
    d = d * t;                               // edx = (R8.tx>>8)*(RDX.a>>2)  0x180006d3e
    t = RDX[1] >> 2;                         // eax = *(rbx+4) >>2    0x180006d41, 0x180006d44
    c = c * t;                               // ecx = (R8.ty>>8)*(RDX.b>>2)  0x180006d47
    d = d - c;                               // edx -= ecx            0x180006d4a
    d = d >> 6;                              // sar 6 (signed)        0x180006d4c
    d = d + RDX[2];                          // += *(rbx+8) = RDX.tx  0x180006d4f
    out[2] = d;                              // *(rcx+8) = tx_out     0x180006d52

    // ========================================================================
    // BLOCK 4 — out[3] = ty_out = ((R8.tx>>8?)... ) symmetric +
    //   ACTUAL:  out[3] = ((R8.ty>>8)*(RDX.a>>2) + (R8.tx>>8)*(RDX.b>>2)) >> 6
    //                              + RDX.ty
    //   i.e. ty_out = RDX.ty + ( RDX.a*R8.ty + RDX.b*R8.tx ) >> 16
    //   = (t_RDX + R_RDX · t_R8).y
    //   NOTE the operand pairing: r8d uses (R8.tx? ) — see exact reads below.
    // ========================================================================
    c = R8[2] >> 8;                          // ecx = *(r11+8)  >>8   0x180006d55, 0x180006d64
    int r8v = RDX[0] >> 2;                   // r8d = *(rbx)    >>2   0x180006d59, 0x180006d60
    t = R8[3] >> 8;                          // eax = *(r11+0xc)>>8   0x180006d5c, 0x180006d67
    // rdx := &out[1]  (set up the 2nd arg for the tail call)        0x180006d6a (lea rdx,[rdi+4])
    r8v = r8v * t;                           // r8d = (RDX.a>>2)*(R8.ty>>8)  0x180006d6e
    t = RDX[1] >> 2;                         // eax = *(rbx+4)  >>2   0x180006d72, 0x180006d75
    c = c * t;                               // ecx = (R8.tx>>8)*(RDX.b>>2)  0x180006d78
    r8v = r8v + c;                           // r8d += ecx            0x180006d7b
    // rcx := out  (1st arg for the tail call)                       0x180006d7e (mov rcx,rdi)
    r8v = r8v >> 6;                          // sar 6 (signed)        0x180006d81
    r8v = r8v + R8[3];                       // += *(rbx+0xc) = RDX.ty 0x180006d85  (reads rbx, see note)
    out[3] = r8v;                            // *(rcx+0xc) = ty_out   0x180006d89

    // ---- epilogue ----
    //   rbx = [rsp+0x30] ; add rsp,0x20 ; pop rdi                   0x180006d8d/d92/d96

    // ---- tail call: renormalize the composed rotation (out.a,out.b) to Q16 unit ----
    //   rcx = out (=&out[0]) , rdx = &out[1]
    sub_180006c40(&out[0], &out[1]);         // jmp 0x180006c40       0x180006d97
}
```

### Exact field-read disambiguation (Blocks 3 & 4)

Because the same `rbx`(=rdx operand) and `r11`(=r8 operand) pointers feed both
translation blocks, here is the literal source for each multiply term — port from
these, not from the prose:

| out field | term 1 (signed) | term 2 (signed) | combine | += base |
|-----------|-----------------|------------------|---------|---------|
| `out[2]` (tx) | `(*(r8+0x8) >>8) * (*(rdx+0x0) >>2)` | `(*(r8+0xc) >>8) * (*(rdx+0x4) >>2)` | `(t1 - t2) >> 6` | `+ *(rdx+0x8)` |
| `out[3]` (ty) | `(*(rdx+0x0) >>2) * (*(r8+0xc) >>8)` | `(*(r8+0x8) >>8) * (*(rdx+0x4) >>2)` | `(t1 + t2) >> 6` | `+ *(rdx+0xc)` |

(`rdx` here = the `rbx`-cached operand; `r8` = the `r11`-cached operand.) So:
- `tx_out = RDX.tx + ( RDX.a·R8.tx − RDX.b·R8.ty ) >> 16`
- `ty_out = RDX.ty + ( RDX.a·R8.ty + RDX.b·R8.tx ) >> 16`

This is exactly `t_RDX + R(RDX) · t_R8` — i.e. R8's translation is rotated by
RDX's rotation and added to RDX's translation. (The base `+= RDX.tx/ty` in blocks
3/4 is `*(rbx+8)`/`*(rbx+0xc)`, the RDX operand.)

### Fixed-point reasoning

Rotation blocks (1,2): each operand pre-shifted `>>1` (÷2 each, ÷4 total), the
product is then `+0x2000` rounded and `>>14`. Net: `(p·q)/4 / 16384 = (p·q)/65536`
= a Q16×Q16 → Q16 multiply with round-half-up (`0x2000 = 1<<13 = ½·2^14`). So
`out.a = (A.a·B.a − A.b·B.b) >> 16`, `out.b = (A.a·B.b + A.b·B.a) >> 16` — the
complex/rotation product, in Q16.

Translation blocks (3,4): rotation operand `>>2`, translation operand `>>8`
(÷4 · ÷256 = ÷1024), product then `>>6` (÷64). Net ÷65536 = Q16 multiply, **no**
explicit rounding constant (truncating). The asymmetric `>>2`/`>>8` split keeps the
intermediate `int32` from overflowing when `tx,ty` can be large pixel/Q-values.
Then the matching translation component is added directly (it is already in the same
units as the `>>6` result, hence `tx,ty` are stored as plain values, *not* Q16-scaled
the way `a,b` are — see open question).

Renormalization (tail call): `out.a²+out.b²` after a Q16 rotation product drifts a
few ulps off `0x10000²`; `sub_180006c40` divides both by `isqrt`(magnitude) and
rescales to a Q16 unit vector, so the stored `(a,b)` stays exactly on the unit
circle (matches `decode_sec0_pre.py`'s "every record has `a²+b² == 0x10000²`" check).

## Callees

- `0x180006c40` — **2D-vector → Q16 unit-vector normalization** (tail `jmp` at
  0x180006d97). Called as `sub_180006c40(&out.a /*rcx*/, &out.b /*rdx*/)` to
  renormalize the freshly-composed rotation `(out.a, out.b)` back onto the unit
  circle in Q16 (it does `mag=isqrt(a²+b²)`, then `a,b = a,b·65536/mag`). It
  itself calls `0x180003060` (unsigned isqrt). See `func_180006c40.md`.

## GDB verification hooks

Windows x64: `rcx`=out, `rdx`=RDX operand, `r8`=R8 operand at entry. Set:

1. **Entry — dump both input transforms** `break *0x180006cc0`
   - `x/4wd $rdx` → RDX = {a, b, tx, ty} (first-applied transform)
   - `x/4wd $r8`  → R8  = {a, b, tx, ty} (second-applied transform)
   - save `$rcx` (out ptr) to re-read at exit.
   Verify the inputs are rigid: `RDX.a² + RDX.b² ≈ 0x10000²` and same for R8.

2. **After out.a (rotation cos) is written** `break *0x180006d04`
   - `p/d $r10d` → `out.a = (RDX.a·R8.a − RDX.b·R8.b) >> 16` (just stored to `*(rcx)`)
   - `x/wd $rdi` → confirm `*out == out.a`.

3. **After out.b (rotation sin) is written** `break *0x180006d2b`
   - `p/d $eax`  → `out.b = (RDX.a·R8.b + RDX.b·R8.a) >> 16` (stored to `*(rcx+4)`)
   - `x/wd $rdi+4`.
   Sanity: `out.a²+out.b² ≈ 0x10000²` **before** renorm (small drift expected here).

4. **After out.tx is written** `break *0x180006d55`
   - `p/d $edx`  → `out.tx = RDX.tx + (RDX.a·R8.tx − RDX.b·R8.ty)>>16` (stored to `*(rcx+8)`)
   - `x/wd $rdi+8`.

5. **After out.ty is written** `break *0x180006d8d`
   - `p/d $r8d`  → `out.ty = RDX.ty + (RDX.a·R8.ty + RDX.b·R8.tx)>>16` (stored to `*(rcx+0xc)`)
   - `x/wd $rdi+0xc`.
   These 4 (#2–#5) are the **core composition outputs** — match a Python
   `compose(B, A)` against them field-by-field.

6. **At the tail call (pre-renorm rotation)** `break *0x180006d97`
   - `x/2wd $rcx` → `(out.a, out.b)` *before* normalization (rcx=out, rdx=out+4).
   Step into 0x180006c40 (see func_180006c40.md hooks #4/#5) to capture the
   *post*-renorm `(a,b)` and confirm `a²+b² == 0x10000²` exactly.

7. **Exit (after tail call returns to caller)** — re-read the saved out ptr:
   - `x/4wd <out_addr>` → final `{a, b, tx, ty}`; `a²+b²` should equal `0x10000²`
     within integer rounding (the renorm result).

Priority for the transform port: **#2–#5** (the four composed fields) plus a
step-through of the #6 renorm to reproduce the exact unit-circle snap.

## Confidence & open questions

**Solid (read directly from disasm):**
- Control flow (straight-line, four compute blocks, single tail `jmp`), all
  addresses, all four `out[]` stores and their source expressions.
- The two distinct fixed-point recipes: rotation = `>>1,>>1, +0x2000, >>14`
  (rounded Q16 complex product); translation = `>>2,>>8, >>6` (truncated Q16
  multiply) plus a direct add of the operand's own translation.
- This is rigid-transform composition `R_out=R_B·R_A`, `t_out=t_B+R_B·t_A`,
  followed by rotation renormalization via the tail call to `0x180006c40`.
- Signedness: every shift is `sar` (arithmetic/signed); all `imul`/`lea` operate
  on signed int32. No unsigned ops here.

**Inferred / GUESS:**
- Which operand is "A" (first applied) vs "B" (second). The math is unambiguous
  *structurally* (`rdx`'s rotation rotates `r8`'s translation, and `rdx`'s
  translation is the additive base), so functionally:
  `out = compose(left=rdx, right=r8)` where `out.t = rdx.t + R(rdx)·r8.t`. I
  labeled `rdx`=A/"first" and `r8`=B/"second" in the signature prose; if your
  caller convention is the opposite, swap the names — the field formulas in the
  disambiguation table are the ground truth regardless.
- `tx,ty` scaling: the rotation fields are Q16 (×65536); the translation fields
  are combined via a Q16 multiply but the additive base (`+= *(rbx+8)`) is added
  raw, implying `tx,ty` are stored in the **same unit as the matrix output**,
  consistent with `sec0_pre`'s `tx/65536` interpretation in `decode_sec0_pre.py`.
  Exact unit (pixels·65536 vs raw) is a caller-side question.

**Open questions:**
- The renormalization tail call assumes the rotation drifted; confirm with hook
  #3 vs #6 that pre-renorm `(a,b)` is within a few ulps of unit and post-renorm
  snaps to `a²+b²==0x10000²`.
- Who calls `sub_180006cc0` and in what order they pass the pairwise transforms
  (this determines whether the table stores `T_i→j` or `T_j→i`). Determined by
  callers (the `bdf0` pairwise-table builder feeding `sec0_pre`), not by this fn.
