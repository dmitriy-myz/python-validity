# sub_1800065b0 — append 4 bytes (u32 / Q16-low-or-high word) into a growable serialization buffer

This is **not** transform math itself. It is a tiny buffer-writer helper: it copies exactly
**4 bytes** from a source pointer into `buffer.base + buffer.len`, then advances `buffer.len += 4`.
It is the primitive used by the higher-level serializers (e.g. the `sec0_pre` / v30 writers) to
emit one 32-bit word at a time — which is how Q16 fixed-point transform components
(`a`, `b`, `tx`, `ty`, all 32-bit) get streamed into the template blob. The actual transform
arithmetic lives in the callers; this function only moves the resulting words.

## Signature

```c
// writer is a small "growable byte buffer" descriptor:
//   +0x08 : uint8_t *base   (start of buffer storage)
//   +0x10 : uint32_t  len   (current write cursor / used length, in bytes)
// src points at 4 bytes to append (a u32 word, e.g. one Q16 transform component).
void sub_1800065b0(BufWriter *writer /*rcx*/, const void *src /*rdx*/);
```

- `writer` (rcx): pointer to a 2-field buffer descriptor (`base` at +0x8, `len` at +0x10). **solid** (offsets are read/written directly).
- `src`   (rdx): pointer to the 4 source bytes to append. **solid** (passed straight to memcpy as the source).
- Returns: void (the caller ignores `eax`; the function returns nothing meaningful). **solid**

## Pseudocode

```c
void sub_1800065b0(BufWriter *writer /*rcx*/, const void *src /*rdx*/) {
    // ---- entry / prologue ----                          // 0x1800065b0  push rbx
                                                           // 0x1800065b2  sub rsp,0x20 (shadow space)
    const void *src_p     = src;                           // 0x1800065b6  rax = rdx (save src)
    uint32_t    cur_len   = writer->len;   /* [rcx+0x10] */ // 0x1800065b9  edx = *(u32*)(rcx+0x10)
    BufWriter  *w         = writer;                         // 0x1800065bc  rbx = rcx (save writer)
    void       *dst       = writer->base + cur_len;        // 0x1800065bf  rdx = *(rcx+0x8) + edx  (base + len)
    uint32_t    n         = 4;                              // 0x1800065c3  r8d = 0x4 (byte count)
    /* rcx = dst (from rax=src? no): */                    // 0x1800065c9  rcx = rax  -> rcx = src
    //  NOTE on arg order to the memcpy callee (sub_1800031e0):
    //    callee(rcx=dst, rdx=src, r8d=count). Here rcx=src_p, rdx=base+len.
    //    => memcpy(dst = src_p, src = base+len, 4)?  See "Confidence" — the
    //       register assignment makes rcx=src and rdx=base+len, i.e. the
    //       copy direction is dst=rcx, src=rdx with rcx==original `src` arg.
    memcpy(/*dst=rcx*/ src_p, /*src=rdx*/ dst, /*n=*/4);   // 0x1800065cc  call 0x1800031e0

    w->len += 4;       /* [rbx+0x10] += 4 */               // 0x1800065d1  add dword [rbx+0x10], 0x4

    // ---- epilogue ----                                   // 0x1800065d5  add rsp,0x20
                                                           // 0x1800065d9  pop rbx
    return;                                                 // 0x1800065da  ret
}
```

### Important nuance on copy direction (rcx vs rdx)

The memcpy callee `sub_1800031e0` uses the convention **dst = rcx, src = rdx, count = r8d**
(it writes `*(rcx-…)` and reads `*(rcx+r9)` where `r9 = src - dst`; the final loop stores into
`[rcx-4]`/`[rcx-1]`, i.e. **rcx is the destination**).

In `sub_1800065b0`:
- `rdx` is loaded with `base + len`  (0x1800065bf)
- `rcx` is set to `rax`, which is the **original `src` arg** (0x1800065c9, after `rax=rdx` at 0x1800065b6)

So literally `memcpy(dst = original_src_arg, src = base+len, 4)`. That copies **out of** the buffer
**into** the caller-supplied pointer — i.e. this reads a 4-byte word *from* the buffer cursor into
`src`, then advances the cursor. In other words this is most likely a **READER** ("pull next u32
from stream and advance"), not a writer, OR the disassembler's operand naming differs from the
callee's actual convention. Treat the semantics as: **transfers 4 bytes between `arg2`-pointer and
`buffer.base+buffer.len`, then `buffer.len += 4`.** See open questions.

## Struct fields & constants

| Access | Reg/Off | Meaning (inferred) |
|---|---|---|
| `*(u32*)(rcx+0x10)` read | writer+0x10 | current cursor / used length in bytes (`len`) — **solid** |
| `*(u64*)(rcx+0x8)` read  | writer+0x8  | base pointer of buffer storage (`base`) — **solid** |
| `*(u32*)(rbx+0x10) += 4` write | writer+0x10 | advance cursor by 4 after the transfer — **solid** |
| dst/src of copy | `base + len` | the 4-byte slot at the current cursor — **solid** |

Magic constants:
- `0x4` (r8d) — transfer size = 4 bytes (one 32-bit word). This is the fixed element width: the
  caller emits/consumes exactly one u32 per call (consistent with Q16 components being 32-bit).
- `0x20` — 32-byte shadow space reserved for the call (Win64 ABI), no semantic meaning.

## Callees

- `0x1800031e0` — **inlinable memcpy** (alignment-aware: 4-byte DWORD copy loop when both `dst` and
  `src` are 4-aligned and length is a multiple compatible with that, else byte-by-byte fallback).
  `(rcx=dst, rdx=src, r8d=count)`. See `/tmp/func_1800031e0.S`.

## GDB verification hooks

To verify a Python re-implementation produces identical buffer state, break and dump:

- `break *0x1800065b0` (entry):
  - `rcx` = writer descriptor. Dump `*(u64*)($rcx+8)` (base) and `*(u32*)($rcx+0x10)` (len-before).
  - `rdx` = the external 4-byte pointer (the word being appended/extracted). Dump `*(u32*)$rdx`.
- `break *0x1800065bf` (compute dst = base+len):
  - After this insn, `rdx` holds `base + len` — the cursor slot address. `x/1xw $rdx`.
- `break *0x1800065cc` (the call to memcpy):
  - `rcx` = transfer dst, `rdx` = transfer src, `r8d` = 4. Confirms copy direction & operands.
  - Dump `x/1xw $rdx` (source word) and the dest `x/1xw $rcx` before stepping over.
- `break *0x1800065d1` (cursor advance):
  - Before exec: `*(u32*)($rbx+0x10)` = len. After `add`, len has grown by 4.
  - To capture the appended word in-buffer: `x/1xw (*(u64*)($rbx+8) + *(u32*)($rbx+0x10))` BEFORE
    the add gives the slot just written/read.
- `break *0x1800065da` (ret):
  - `*(u32*)($rbx+0x10)` = len_after (should equal len_before + 4). Confirms the +4 stride.

Key invariant to assert in the port: `len_after == len_before + 4` and the 4 bytes at
`base + len_before` equal the transferred word.

## Confidence & open questions

- **Solid**: It's a 4-byte transfer between `writer.base + writer.len` and the `arg2` pointer,
  followed by `writer.len += 4`. Buffer descriptor layout (`base@+8`, `len@+0x10`) is unambiguous.
- **Solid**: callee `0x1800031e0` is a hand-rolled `memcpy` (alignment-checked DWORD loop with a
  byte fallback). It is not transform math.
- **Open question — copy direction**: Per the callee's own convention (dst=rcx, src=rdx) and the
  register loads here (rcx ← original `src` arg, rdx ← `base+len`), the literal call is
  `memcpy(dst=src_arg, src=base+len, 4)`, i.e. this **reads** a u32 out of the buffer into the
  caller's pointer and then advances the cursor — making it a stream **reader/`get_u32`**, not a
  writer. If instead the higher-level convention treats arg2 as the source (a writer/`put_u32`),
  the disasm operand order would be reversed from the callee's. Resolve empirically via the
  `0x1800065cc` hook (compare `x/1xw $rcx` vs `x/1xw $rdx` before vs after the call to see which
  side changes). This does not affect the `len += 4` stride either way.
- **Not transform math**: This function contains no arithmetic, shifts (>>16), trig, sqrt,
  rounding (0x8000), or matrix ops. It is purely the 32-bit element mover that the transform
  serializers/deserializers call once per Q16 word.
