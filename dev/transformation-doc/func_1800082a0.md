# sub_1800082a0 — top-level frame-registration orchestrator (allocates scratch geometry vectors, registers the base frame, builds reference label-map, runs the forward/reverse candidate→evaluate→commit loop that fills sec0_pre)

This is **one of the two root functions** of the geometry/registration pipeline.
By itself it contains **no rigid-transform math** — it is the *scaffold* that:

1. Gates on a status byte (`sub_18000b400` / `sub_18000b3d0`) deciding a `mode` flag.
2. Allocates ~9 scratch buffers of `n` (and `4n`, `16n`, `align4(n)`) elements via the
   vector-grow helper `sub_180003320` (each call returns a 0x30-byte vector header that is
   copied back into the `[rsp+0x100]` working header, and the data pointer is stashed into a
   dedicated `[rsp+0xNN]` slot).
3. Registers the **base / seed frame** into the geometry table (`sub_180007fe0`).
4. Rasterizes the reference keypoint boxes into a `w*h` **label map** (`sub_180003ac0`),
   then `memset`s a 0xFA-byte (250) presence array, builds reference correspondence index
   lists (`sub_1800041d0`), and marks the presence map (`sub_180004190`).
5. Runs a **2-iteration loop** (`b = 0,1` — forward then reverse frame role):
   - `sub_1800077d0` → build candidate (j, idxB) correspondences + composed Q16 Xforms,
   - `sub_180007b30` → per-candidate reproject/score/**commit accepted frames into sec0_pre**,
   - `sub_1800031e0` → grow/append a result list by `4*frameCount` bytes.
6. Final cleanup pass `sub_180008160` (walks the committed geometry table) and a `memset` to 0.

All the **Q16 similarity-transform arithmetic** (R=[[a,-b],[b,a]], t=(tx,ty), `>>16`,
`0x8000` rounding) lives **inside the callees** — principally `sub_180006cc0` (the
B∘A transform composer, reached via `sub_1800077d0` / `sub_180007b30` / `sub_1800041d0`).
This root function only *moves vectors around and sequences those callees*.

## Signature

Windows x64. The first 4 args are in registers; args 5+ come off the caller's stack.
Because this function pushes 7 regs (`rbx,rbp,rsi,rdi,r12,r13,r14,r15` → note rbx is saved
to shadow `[rsp+0x10]`, the other 7 are `push`ed) and then `sub rsp,0x6a0`, the inbound stack
args land at `[rsp+0x6a0 + 8*7 + 8(ret) + 8*N]`. Concretely the prologue reads them as:

| inbound slot | read at | reg/var | inferred meaning |
|---|---|---|---|

| arg2 | dl | `flag0` (`[rsp+0xa0]`) | a bool, stored & forwarded |
| arg3 | r8 → r14 | `srcA` | pointer to frame-A keypoint/desc struct |

`n` (=r15d, `frameCount`) is the master sizing parameter. Several derived counts:
`4*n` (=ebx, used for byte arrays), `16*n` (=r8d after `shl 4`), `align4(n)=(n+3)&~3`
(=eax at 0x1800084ef, stored into `[rsp+0xd8]`).

## Pseudocode

Notation: `VEC = (HeaderStruct at [rsp+0x100])` is a reusable 0x30-byte vector descriptor.
`grow(VEC, count, &outPtr)` ≜ `rax = sub_180003320(&VEC_dst[rsp+0x140], &VEC[rsp+0x100], count, &outPtr); copy 0x30 bytes *rax→VEC`.
This idiom (call + the long run of `mov [rdx+0xNN]` copies) appears ~9 times; I collapse it to `grow(...)` and keep the call address + the `&outPtr` slot.

// grow #6: count = 4n -> [rsp+0xf8]

//   r9 = ptr[rsp+0xf0] (grow#4 data, 16n)        [rsp+0x30]=&self ...

> Reading note: the long `mov rcx,[rax]; mov [rdx],rcx; ... ; mov [rdx+0x28],rax` runs
> after each `call 0x180003320` are the **0x30-byte copy of the returned vector header back
> into the working header `[rsp+0x100]`** — they are mechanical and carry no math. The only
> per-grow datum that matters is the *count* passed in `r8d` and the *output data-pointer slot*
> passed in `r9` (the `[rsp+0xNN]` lea). Those are annotated above.

## Callees

- `0x18000b400` — status-range gate: `(statusA<=0x1e && statusB<=0x37)?1:0`. **Early-out** if 0. (leaf; see func_18000b400 if doc'd)
- `0x18000b3d0` — second status-range gate: `(statusA<=0x1e && statusB<=0x31)?1:0` → sets `mode`.
- `0x180003320` — vector grow/reserve-and-get-slot helper (returns 0x30-byte header; data ptr via 4th-arg out). Called 9×. See func_180003320.md.
- `0x180007fe0` — register/initialize the **base frame slot** in the geometry table (bookkeeping, not math). See func_180007fe0.md.
- `0x1800031c0` — guarded `memset`/zero (or free) helper (`if (n>0) memset(dst, val, n)` style). Used for the 0xFA presence array and the final align4(n) cleanup. See func_1800031c0.md.
- `0x180003ac0` — rasterize box list into the `w*h` **label/mask** buffer. See func_180003ac0.md.
- `0x1800041d0` — **transform-and-sample correspondence builder** (Q16 reproject + bounds-test + descriptor/orientation compare). Reaches the real transform math. See func_1800041d0.md.
- `0x180004190` — scatter-mark presence byte-map from an index list (leaf). See func_180004190.md.
- `0x1800077d0` — per-frame candidate-correspondence builder: ROI-gate keypoints, **compose pose with frame transform** (via `sub_180006cc0`), emit (j,idxB) pairs + composed Xforms. See func_1800077d0.md.
- `0x180007b30` — **per-candidate frame-pair evaluator**: reproject, score correspondences, accumulate weighted means, and **commit accepted frames into the sec0_pre geometry table**. The heart of registration. See func_180007b30.md.
- `0x1800031e0` — vector append/grow (result list, by `4n` bytes). See func_1800031e0.md.
- `0x180008160` — final cleanup pass: walk committed geometry table (stride 0x14, gate via `sub_18000b3f0`). See func_180008160.md (not yet written — sibling of this doc).

## GDB verification hooks

Use these to compare a Python re-implementation's intermediate state. (`break *0x...`.)

1. **`break *0x180008341`** (entry gate inputs) — dump `cl` = statusB, `dl` = statusA, and after
   stepping over, `eax` = gate result. Also dump `rbx`(=self), `r13`(=self+0x68). Confirms the
   early-out condition and that you read the right status bytes.
2. **`break *0x18000835a` / `*0x180008379`** — dump `eax` (second-gate result) then `[rsp+0xe0]`
   = `mode`. Verify your `mode = (statusA<=30 && statusB<=49)` matches.
3. **`break *0x180008371`** — dump `r15d` (=`n`, frameCount) and `ebx` (=`4n`). This pins the
   master sizing parameter; everything downstream scales by it.
4. **At each `call 0x180003320`** (0x18000839e, 0x1800083f4, 0x18000844a, 0x1800084a4,
   0x180008508, 0x18000855e, 0x180008654): break and dump `r8d` (count requested) and, *after
   return*, the data pointer written to the corresponding `[rsp+0xNN]` slot
   (`[rsp+0xe8]`,`[rsp+0xc8]`,`[rsp+0xb8]`,`[rsp+0xf0]`,`[rsp+0xc0]`,`[rsp+0xf8]`,`[rsp+0xa8]`).
   Confirms buffer counts: `4n,4n,4n,16n,align4(n),4n,w*h`.
5. **`break *0x180008634`** — dump `r8d` = `w*h`, and read `*(int)(rdi)` (w) and `*(int)(rdi+4)` (h).
   Then **`break *0x1800086a4`** (entry to rasterizer) — dump `rcx`(labelmap ptr), `rdx`(boxes ptr),
   `r8b`(h), `r9b`(w). After return you can hexdump `*[rsp+0xa8]` for `w*h` bytes (the label map).
6. **`break *0x1800086b9`** (after the 0xFA memset) — confirm `[rsp+0x190]..[rsp+0x190+0xFA]` is all 0.
7. **`break *0x18000872b`** (entry to `sub_1800041d0`) and **`*0x180008730`** (after) — dump
   `[rsp+0xa4]` (=`r11d`, reference correspondence count) and `[rsp+0xd0]`. These are the
   reference keypoint counts that seed the loop; compare to your Python's reference list length.
8. **`break *0x1800087de`** (entry to `sub_1800077d0`, inside loop) — dump loop var `ebx` (=b, 0 or 1),

   `16n` bytes = `n × {int32 a, int32 b, int32 tx, int32 ty}` (R=[[a,-b],[b,a]] scaled 1<<16).
9. **`break *0x1800088ae`** (entry to `sub_180007b30`, the COMMIT step — highest priority) — dump
   `ecx`(=`r11d`, candidate count), `rdx`(=&self/[rsp+0xb0]), and the input buffer ptrs in
   `[rsp+0x20..0x30]`. This is where accepted frames get written into sec0_pre, so set a follow-on
   break inside `sub_180007b30` (and ultimately `sub_180006cc0`) to capture the final committed
   transforms. After this call, dump the geometry table reachable from `self+0x68`.
10. **`break *0x1800088cb`** — `sub_1800031e0` append; dump `r8d` (=`4n`) and `rdx`(=`*[rsp+0xf8]`)
    to see what gets appended to the result list per pass.
11. **`break *0x1800088f9`** (final `sub_180008160`) — dump `rcx`(=outListB/r12) and `rdx`(=outListA/rbp).
    Hexdump both vectors here to capture the **final per-frame index/result lists** after both passes.

## Confidence & open questions

**Solid:**
- Control flow is exact: two status-range gates, an early-out, six+one `grow()` allocations with the
  shown counts (`4n`,`4n`,`4n`,`16n`,`align4(n)`,`4n`,`w*h`), a 0xFA(250) memset, a reference
  correspondence build, then a **2-iteration loop** of `sub_1800077d0`→`sub_180007b30`→`sub_1800031e0`,
  and a final `sub_180008160`. All call addresses and the loop bound (`cmp ebx,2; jb`) are verbatim.
- The `0x180003320`+`mov`-run idiom is a vector-header copy; only `count` (r8d) and the out-ptr (r9) matter.
- This function does **no** fixed-point/trig/matrix arithmetic itself — confirmed by absence of any
  `imul`/`sar`/`shr 0x10`/`0x8000`/`0x10000` math beyond the integer sizing (`*4`, `*16`, `align4`,
  `w*h`). The Q16 similarity transforms are produced/consumed by the callees (chiefly `sub_180006cc0`
  reached via 1800077d0 / 180007b30 / 1800041d0).

**Inferred / guesses (marked):**
- The exact semantics of arg4 (`srcB`, r9→[rsp+0x130]) and arg10 (`auxCount`, [rsp+0x728]→[rsp+0xd8])
  are best-effort; `[rsp+0xd8]` is later overwritten by `align4(n)`, so the inbound value's only use
  is as the vector-grow init in the base-frame registration.
- The `mode` flag's downstream effect (`[rsp+0xe0]`→`[rsp+0x98]` into `sub_180007b30`) is named but its
  precise meaning lives in `sub_180007b30`.
- Field names `width/height/boxes` for `dims` (+0/+4/+0x10) are inferred from the `imul w*h` →
  `sub_180003ac0(labelmap,boxes,h,w)` usage; consistent with the rasterizer doc.
- The exact contents of the 4 reference-list output arrays (`[rsp+0x290/0x390/0x490/0x590]`) are
  defined by `sub_1800041d0`; treat that doc as the authority for their layout.
- `0x180008160` has no sibling doc yet; its role (walk geom table, stride 0x14, `sub_18000b3f0` gate)
  is read directly from its disasm here and should be documented separately.

**Open:**
- Whether the `intParam0` (arg7) is an iteration/threshold count or a frame id — only forwarded.
- Confirm via hook #9 that *both* loop passes write distinct entries (forward A→B vs reverse B→A) into
  the same sec0_pre table, or whether pass `b` selects role via the `(b+1)` byte at `[rsp+0x90]`.
