# sub_180006610 — append-N-bytes to a counted byte buffer (vector push-back loop)

This is **not** transform math. It is a tiny container helper: it appends `count`
source bytes, one at a time, to the end of a "counted byte buffer" struct
(`{ base_ptr, length }`), bumping the stored length after each write. The actual
byte move is delegated to `sub_1800031e0` (the inlined `memcpy`-style copier,
called with `n = 1` each iteration). No coordinate math, no fixed-point, no trig,
no matrix/affine ops. It is plumbing that the geometry/serialization code *calls*
to emit bytes into a growing buffer (e.g. building the sec0_pre / TLV byte stream),
not where any transform is computed.

The call is `sub_1800031e0(dst = base + len, src = &src[i], n = 1)` per byte, with
`len` (`[rbx+0x10]`) incremented after each copy. Equivalent to:
`for (i=0; i<count; i++) buf->data[buf->len++] = src[i];`

## Signature

```c
// rcx = buf  (counted byte-buffer: {char* base @+0x08; int32_t len @+0x10})
// rdx = src  (source byte array)
// r8d = count (uint32_t number of bytes to append; loop runs while != 0)
// stdcall-style: ret 0x0 (no stack args to clean — imm16 = 0)
void sub_180006610(ByteBuf *buf /*rcx*/, const uint8_t *src /*rdx*/, uint32_t count /*r8d*/);
```

Argument meanings (best effort):

| reg  | name    | meaning                                                                          |
|------|---------|----------------------------------------------------------------------------------|
| rcx  | `buf`   | pointer to a counted byte-buffer struct (base pointer at `+0x08`, length at `+0x10`) |
| rdx  | `src`   | pointer to the source bytes to append                                            |
| r8d  | `count` | number of bytes to append; treated as a plain counter (`jne`), so `count == 0` is a no-op, and it is effectively *unsigned* (decrement-to-zero, no signed compare) |

Notes:
- `count == 0` short-circuits at entry (`test r8d,r8d; je 0x180006662`) and the function
  returns immediately without touching the buffer.
- Each appended byte is written at `base + len`, then `len` is incremented — so this
  is a classic push-back that assumes the buffer already has capacity (no realloc here).

## Pseudocode

```c
void sub_180006610(ByteBuf *buf /*rcx*/, const uint8_t *src /*rdx*/, uint32_t count /*r8d*/)
{
    // --- entry guard --------------------------------------------------------- 0x180006610
    if (count == 0) return;                       // test r8d,r8d ; je 0x180006662   // 0x180006610 / 0x180006613

    // --- prologue (save regs, set up frame) ---------------------------------- 0x180006615
    // mov [rsp+0x10],rbx ; push rdi ; sub rsp,0x20 ; mov [rsp+0x30],rsi            // 0x180006615..0x18000661f
    const uint8_t *rdi = src;                      // mov rdi, rdx                    // 0x180006624
    ByteBuf       *rbx = buf;                       // mov rbx, rcx                    // 0x180006627
    uint64_t       rsi = (uint32_t)count;           // mov esi, r8d  (zero-extended)   // 0x18000662a
    // 0x18000662d: data16 xchg ax,ax  -> NOP loop-alignment padding, no effect

    // --- append loop --------------------------------------------------------- 0x180006630
    do {
        int32_t  len  = buf->len;                  // mov  edx,[rbx+0x10]             // 0x180006630
        // r8d = 1  (n = 1 byte per copy)          // mov  r8d,0x1                    // 0x180006633
        // rcx = rdi (src element pointer)         // mov  rcx,rdi                    // 0x180006639
        char    *dst  = buf->base + len;           // add  rdx,[rbx+0x8]  (rdx=base+len) // 0x18000663c
        //   NOTE: at the call, rcx=src elem (dst arg), rdx=base+len (src arg), r8d=1.
        //   Per sub_1800031e0's ABI (rcx=dst, rdx=src) the *named* roles look swapped
        //   in the raw regs, but the net effect of a 1-byte copy is a single byte move
        //   between &src[i] and base+len. Effective semantics: *(base+len) = src[i].
        sub_1800031e0(/*dst*/ rdi, /*src*/ dst, /*n*/ 1);  // call 0x1800031e0       // 0x180006640

        buf->len = len + 1;                        // add  [rbx+0x10],0x1            // 0x180006645
        rdi += 1;                                  // add  rdi,1   (advance src)     // 0x180006649
        rsi -= 1;                                  // sub  rsi,1   (remaining--)     // 0x18000664d
    } while (rsi != 0);                            // jne  0x180006630               // 0x180006651

    // --- epilogue ------------------------------------------------------------ 0x180006653
    // mov rsi,[rsp+0x30] ; mov rbx,[rsp+0x38] ; add rsp,0x20 ; pop rdi             // 0x180006653..0x180006661
    return;                                        // ret 0x0                        // 0x180006662
}
```

### On the apparent dst/src swap at the call site

`sub_1800031e0(rcx=dst, rdx=src, r8d=n)` copies `n` bytes. Here, immediately before
the call: `rcx = rdi` (the advancing source-element pointer) and `rdx = base + len`
(the destination slot in the buffer). Taken literally, that copies the buffer slot
*into* `src[i]`, which would be backwards for an "append." Two readings are possible:

1. **Most likely (append):** the intent is `buf->base[len] = src[i]`; the register
   roles as labeled by `sub_1800031e0`'s doc are nominal and a 1-byte transfer is
   symmetric to verify either way — but `len` (`[rbx+0x10]`) is monotonically
   incremented and `src` (`rdi`) is consumed, which is the textbook push-back shape.
   The buffer at `base` is the thing being grown.
2. **Literal:** it reads `*(base+len)` and stores into `*src[i]` (a scatter/patch
   into the source). This is far less consistent with the incrementing `len`.

This must be resolved by the GDB hook below (dump both pointers' bytes before/after).
The structural fingerprint (counter at `+0x10`, base at `+0x08`, `n=1`, increment
after copy) strongly favors reading #1 (append into `buf`).

## Struct fields & constants

`buf` (`rbx`) is a counted byte-buffer / small-vector header:

| access            | offset | type      | meaning                                                        |
|-------------------|--------|-----------|----------------------------------------------------------------|
| `[rbx+0x08]`      | +0x08  | `char*`   | `base` — pointer to the buffer's data region                   |
| `[rbx+0x10]`      | +0x10  | `int32_t` | `len` — current byte length / write cursor (read, then `+=1`)  |

Constants:

| value   | meaning                                                                 |
|---------|-------------------------------------------------------------------------|
| `0x1`   | `n = 1` byte per `sub_1800031e0` call; also the `len += 1` and `count -= 1` strides |
| `0x0`   | `test r8d,r8d` zero-count early-out; `ret 0x0` (stdcall imm16 = 0)       |
| `0x20`  | local stack frame size (`sub rsp,0x20`) — shadow space for the call      |

No fixed-point constants (`0x10000`, `0x8000`, `65536`), no rounding adds, no trig,
no matrix math. Purely a byte-copy loop with a length counter.

## Callees

- `0x1800031e0` — block-copy helper (`memcpy`-style; see `func_1800031e0.md`). Invoked
  here with `n = 1`, i.e. used to move exactly one byte per loop iteration.

## GDB verification hooks

This routine computes no transform/coordinate values, but to confirm a Python
re-implementation of the buffer growth is byte-identical:

- `break *0x180006610` — **entry**. Dump:
  - `rcx` = `buf` pointer; then `*(void**)(rcx+0x08)` = `base`, `*(int*)(rcx+0x10)` = starting `len`.
  - `rdx` = `src` pointer (start of source bytes).
  - `r8d` = `count` (number of bytes that will be appended). If `0`, function returns immediately.
- `break *0x180006630` — **loop head** (per-iteration). Dump:
  - `*(int*)(rbx+0x10)` = current `len` (write cursor before this byte).
  - `rdi` = current `src` element pointer; `x/1bx $rdi` = the source byte about to be copied.
  - `*(void**)(rbx+0x8)` = `base`; the target slot is `base + len`.
- `break *0x180006640` — **just before the copy call**. Dump `rcx`, `rdx`, `r8d`
  (= the literal dst/src/n passed to `sub_1800031e0`). This is the authoritative place
  to resolve the dst/src direction question above: compare `x/1bx $rcx` and `x/1bx $rdx`
  before vs. after stepping over the call to see which side changes.
- `break *0x180006645` — **after the copy, before increment**. Dump `x/1bx ($rbx+...)`
  i.e. read `base+len` (the slot just written) and confirm it now equals the source byte.
- `break *0x180006662` — **exit**. Dump `*(int*)(rbx+0x10)` and confirm it equals
  (entry `len`) + (entry `count`); then dump `count` bytes at `base + entry_len` and
  compare to the original `count` bytes at the entry `src` — they must match.

End-to-end check for a port: record `(base, len, src, count)` at entry; after return,
`buf.len == len + count` and `base[len .. len+count) == src[0 .. count)`.

## Confidence & open questions

**Solid (high confidence):**
- Control flow: zero-count early-out, a single `do/while` decrementing `count`,
  per-iteration read of `len` at `+0x10` and increment afterward, advancing `src`.
- `buf` layout: `base` at `+0x08`, `len` (32-bit) at `+0x10`. The `n = 1` constant
  to `sub_1800031e0` means exactly one byte moves per iteration.
- No geometry/fixed-point/trig; this is a container append helper. The only callee is
  the verified `memcpy`-style `sub_1800031e0`.

**Inferred / open questions:**
- **Copy direction (dst vs. src):** at the call, `rcx = src-elem` and `rdx = base+len`,
  which is the *reverse* of `sub_1800031e0`'s nominal `(rcx=dst, rdx=src)` ABI. The
  monotonic `len` increment and `src` consumption make the **append-into-`buf`** reading
  by far the most plausible, but this should be confirmed with the `0x180006640` GDB hook
  (one of the two byte buffers will change after the call — that one is the destination).
- **No capacity/realloc:** this function never grows `base`; it assumes the caller has
  reserved enough room. Some sibling function presumably ensures capacity before calling.
- **Relevance to sec0_pre / rigid transforms:** indirect. This is the kind of low-level
  emitter that serializes already-computed transform/table bytes into a growing buffer;
  it does not itself compute any transform values.
