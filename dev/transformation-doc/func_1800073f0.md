# sub_1800073f0 — thin "compute 2D similarity transform → pack into 16-byte out-struct" wrapper

This is a 30-instruction glue/adapter around the real transform-math worker
`sub_180006f20`. It allocates a small scratch frame, hands the worker **four
output int32 pointers** (laid out contiguously on its own stack), forwards its
own stack-borne arguments to the worker, and on success copies the worker's four
resulting `int32`s into the caller-supplied **16-byte output struct** (`rbx` ←
`rcx`). Returns `1` on success, `0` on failure.

All the actual coordinate / fixed-point math lives in `sub_180006f20`
(centroid accumulation, Q16 `*65536` rotation cos/sin, translation; see
`## Callees`). **This wrapper is purely register/stack marshalling + a 16-byte
copy.** It is the twin of `sub_180007390` (same idiom, different worker
`sub_180006e10`), but here the 4 output slots map to the out-struct *in order*
(no interleave).

## Pseudocode

```c
BOOL sub_1800073f0(xform16_t *out /*rcx*/, void *arg_rdx /*rdx*/,
                   void *arg_r8 /*r8*/, int32_t arg_r9d /*r9d*/)
{
    // ---- prologue ----
    // rax = rsp        (anchor: captures pre-push rsp)                 // 0x1800073f0
    // push rbx                                                          // 0x1800073f3
    // sub  rsp, 0x50   (scratch frame; rsp_at_call = anchor-0x58)       // 0x1800073f4

    // ---- spill the 3 forwarded args into the scratch/home area ----
    // *(int32*)(anchor-0x28) = arg_r9d;   // 32-bit store               // 0x1800073f8
    // *(void**)(anchor-0x30) = arg_r8;                                  // 0x1800073fc
    rbx = out;          // save out-struct ptr (rcx)                     // 0x180007400
    // *(void**)(anchor-0x38) = arg_rdx;                                 // 0x180007403

    // ---- build the 4 contiguous output-slot pointers ----
    // These four int32 slots live at anchor-0x18, -0x14, -0x10, -0xc
    // (i.e. [rsp_at_call + 0x40 .. +0x4c]); the worker writes its 4
    // transform components into them.
    int32_t slot0, slot1, slot2, slot3;        // anchor-0x18 .. -0xc
    // r9 = &slot3   (anchor-0xc)                                        // 0x180007407
    // r8 = &slot2   (anchor-0x10)                                       // 0x18000740b
    // rdx= &slot1   (anchor-0x14)                                       // 0x18000740f
    // rcx= &slot0   (anchor-0x18)                                       // 0x180007413

    // ---- call the transform-math worker ----
    // sub_180006f20(&slot0, &slot1, &slot2, &slot3, /*+ stack args:*/
    //               arg_rdx@[rsp+? ], arg_r8, arg_r9d, ...);
    // The worker reads its extra inputs off this frame
    // (the spilled arg_rdx/arg_r8/arg_r9d at anchor-0x38/-0x30/-0x28,
    //  which sit at [rsp_at_call+0x20]/[+0x28]/[+0x30] = the worker's
    //  shadow + 1st stack arg region).
    int eax = sub_180006f20(&slot0, &slot1, &slot2, &slot3);             // 0x180007417  (call 0x180006f20)

    if (eax == 0) goto L_fail;     // test eax,eax ; je 0x180007446      // 0x18000741c / 0x18000741e

    // ---- success: copy the 4 transform components into out[0..3] ----
    // (rsp here = rsp_at_call = anchor-0x58, so [rsp+0x40]=slot0, etc.)
    out->f0 = slot0;   // *(int32*)(rbx+0x0) = *(int32*)(rsp+0x40)       // 0x180007420 / 0x180007424
    out->f4 = slot1;   // *(int32*)(rbx+0x4) = *(int32*)(rsp+0x44)       // 0x180007426 / 0x18000742a
    out->f8 = slot2;   // *(int32*)(rbx+0x8) = *(int32*)(rsp+0x48)       // 0x18000742d / 0x180007431
    out->fc = slot3;   // *(int32*)(rbx+0xc) = *(int32*)(rsp+0x4c)       // 0x180007434 / 0x180007438

    eax = 1;                                                             // 0x18000743b
    // add rsp,0x50 ; pop rbx ; ret                                      // 0x180007440 / 0x180007444 / 0x180007445
    return 1;

L_fail:                                                                  // 0x180007446
    // xor eax,eax ; add rsp,0x50 ; pop rbx ; ret                        // 0x180007446 / 0x180007448 / 0x18000744c / 0x18000744d
    return 0;
}
```

## Callees
- `0x180006f20` — **the transform-math worker.** Computes a 2D rigid/similarity
  transform from (apparently) two point sets: accumulates per-axis sums/centroids
  in a stride-16 loop (0x7000–0x7027), forms cross/auto-correlation products
  (`imul` accumulations 0x7130–0x71c3 and 0x7218–0x724f), then in the epilogue
  (0x7289 `call 0x180003060` = `sqrt`/`hypot`-like; 0x72a9/0x72ac `shl edi/esi,0x10`
  = `*65536`; `idiv r11d` = normalize by magnitude) produces the Q16 cos/sin and
  translation and writes them through its four output pointers
  (`[rsp+0xc0/0xc8/0xd0/0xd8]` ← the 4 slots this wrapper passed). Its own callees
  are `0x180003060` and `0x180006c40`. Full math should be documented in
  `func_180006f20.md` (not yet written) — **decode that next** for the actual
  transform formula; this wrapper only marshals it.

## Confidence & open questions
**Solid (high confidence):**
- Control flow, ABI, and the exact byte/field mapping: 4 args in, `rcx`=out
  saved to `rbx`, three args spilled, 4 contiguous int32 output slots passed to
  `sub_180006f20`, and on `eax!=0` the slots are copied **in order** to
  `out+0x0..+0xc`. Return is `1`/`0`. Every address above is verbatim from the
  disasm.
- This function performs **no arithmetic of its own** — it is pure marshalling.

**Inferred / open:**
- **Field roles `tx/ty/a/b`** come from reading the worker's epilogue
  (`shl …,0x10`, `idiv`, the `sqrt` call), not from this function. They are a
  strong but unconfirmed guess; confirm by decoding `sub_180006f20`.
- **Whether `arg_rdx`/`arg_r8`/`arg_r9d` are truly consumed by the worker via the
  stack.** The wrapper passes only the 4 slot pointers in registers; the worker
  reads many values at `[rsp+0xc0..0xf0]` (output ptrs + scalar `[rsp+0xf0]` used
  as the `idiv` divisor `ebx` and `[rsp+0xe0]/[rsp+0xe8]` as the two point-array
  bases `r14`/`r15`). Those frame offsets correspond to **arguments the *caller*
  of this wrapper placed**, i.e. `sub_1800073f0`'s own stack args beyond r9 —
  meaning this wrapper likely has **more than 4 arguments** (the caller
  `sub_180007480` supplies extra stack args at `[rsp+0x20]…` that pass through to
  the worker). The 4 register args documented here are the ones this function
  actively touches; **the additional pass-through stack args (point-array
  pointers + divisor N) are an open item** — resolve by inspecting the call site
  in `sub_180007480` and the worker's stack-arg reads.
- `arg_r9d` 32-bit store strongly suggests a scalar count/divisor `N`, but its
  exact role is defined in the worker.
