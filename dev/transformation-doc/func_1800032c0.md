# sub_1800032c0 — small struct initializer / aligned-buffer cursor setup (8-byte alignment of a base pointer)

Leaf function (no callees), 25 instructions / 80 bytes (`0x1800032c0`–`0x180003310`). It populates a 6-field, 0x30-byte output struct and returns the pointer to it. It is **not** transform / rigid-2D / fixed-point geometry math. It is a generic struct constructor whose only real computation is rounding a base pointer up to the next 8-byte boundary and recording the padding/remaining-length bookkeeping. This is the classic "placement / arena writer init" idiom (likely an STL-style allocator-result or a serialization-cursor init), the kind that *surrounds* the geometry code rather than performing it.

Behaviour summary: store `begin` into `*pbegin`; initialize `result` with `count=0`, all pointer fields = `end_or_cap`; **if `n <= total`** compute `aligned_cur = align_up_8(begin + n)`, store it at +0x10, and set `count = total - n - (padding)` ... see exact arithmetic below. Return `result`.

{

    cursor_t* r10 = rcx;                   // 0x1800032ca  alias out ptr

    //        So from here on `rax`/`rcx` are integer-zero, not the pointer.
    int32_t ecx = 0;                       // 0x1800032d3  xor ecx,ecx

    *(void**)(r10 + 0x10) = (void*)(int64_t)ecx; // 0x1800032db result->aligned_cur = 0
    *(void**)(r10 + 0x18) = rax;           // 0x1800032df  result->f18 = 0   (rax was cleared)
    *(void**)(r10 + 0x20) = rax;           // 0x1800032e3  result->f20 = 0
    *(void**)(r10 + 0x28) = rax;           // 0x1800032e7  result->f28 = 0

        goto L_ret;                        //              (skip the body when n > total)

    int64_t rcx_n = (int64_t)(int32_t)r8d; // 0x1800032ed  movsxd rcx,r8d  (SIGN-extend n)

### What the arithmetic actually computes (the only "math")

Let `addr = (uintptr)begin + n` (n sign-extended).
* `aligned_cur = (addr + 7) & ~7` — round the address **up** to the next multiple of 8.
* `padding = aligned_cur - addr` (range `0..7`).
* `result->count = total - n - padding` (computed via 32-bit ops: `((addr) - aligned_cur) - n + total`, where `(addr - aligned_cur) == -padding`).

So `count` is "how many of `total` remain after consuming `n` and the alignment padding". No rotation matrix, no Q16 (`0x10000`/`0x8000`), no atan2/sqrt. The `& ~7` is **pointer alignment**, not a fixed-point mask. The `cmp` is a guard: when `n > total` the struct is left zeroed (degenerate/empty).

## Confidence & open questions

**Solid (directly from disasm):**
* Control flow, all 6 struct stores and their addresses, the 8-byte align-up of `(begin+n)`, the `count = total - n - padding` formula, signedness (`movsxd` n, signed `jg`), and `return rcx`.
* This is **not** rigid-transform / Q16 / sec0_pre geometry math. `& ~7` is pointer alignment; there is no `0x10000`/`0x8000`/multiply/atan2/sqrt anywhere.

**Inferred / guesses:**
* Field *names* (`count`, `base_end`, `aligned_cur`, `f18/f20/f28`) and arg names (`pbegin`, `end_or_cap`, `total`). The +0x18/+0x20/+0x28 fields are just zeroed here, so their semantic role is unknown without seeing consumers.
* Whether `n`/`total` are byte counts or element counts — the alignment is byte-granular (`& ~7`) and `begin+n` is treated as a byte address, suggesting **byte** offsets; `count` would then be remaining bytes after alignment. This looks like an allocator/serialization-buffer cursor init (the kind of glue around the template builder), not part of the transform computation itself.

**Open questions:**
* Identity of the 0x30-byte struct and which higher-level function consumes it (would resolve whether this is allocator metadata vs a stream writer). Not needed for the transform port, but worth a one-line note if it shows up adjacent to sec0_pre serialization.
