# sub_180003490 — minimal angular distance on a 180° ring (orientation difference)

Leaf function (no callees), 69 bytes / 23 instructions. Pure integer arithmetic.
Computes the *unsigned* angular difference between two orientations measured in
degrees, where the circle wraps every **180°** (i.e. angle θ and θ+180 are treated
as identical — exactly the convention used for ridge/gradient orientations). One of
the inputs is first shifted by an offset and reduced `mod 180`.

Result is in `[0, 90]`.

## Signature

```c
// All three inputs are read as *bytes* (movzx) for arg1/arg2; arg3 is read as the
// full 32-bit register r8d (so it may be a larger angle/offset, e.g. a per-frame
// rotation in whole degrees). Return is the min circular distance, range 0..90.
int sub_180003490(uint8_t angle_a /*cl*/,      // first orientation, 0..255 (deg)
                  uint8_t angle_b /*dl*/,      // second orientation, 0..255 (deg)
                  int32_t offset  /*r8d*/);    // added to angle_a before mod-180
                                               // (GUESS: rotation applied to frame A)
```

Semantics (verified numerically):
```
a' = (angle_a + offset) % 180          // C truncated modulo (signed)
d  = |a' - angle_b|                     // raw difference
return min(d, 180 - d)                  // wrap on the 180° ring  -> 0..90
```

## Pseudocode

```c
int sub_180003490(uint8_t cl, uint8_t dl, int32_t r8d) {
    uint32_t r10d = (uint8_t)dl;                  // 0x180003490  movzx r10d,dl   (angle_b)
    uint32_t r9d  = (uint8_t)cl;                  // 0x180003494  movzx r9d,cl    (angle_a)
    // eax loaded with the div-by-180 magic constant:
    int32_t  eax  = 0xb60b60b7;                   // 0x180003498  (signed = -1240768329)
    r9d = r9d + r8d;                              // 0x18000349d  add r9d,r8d   -> s = angle_a + offset

    // ---- signed division of r9d by 180 (0xB4) via magic-multiply idiom ----
    //   edx:eax = (int64) eax * (int64) r9d        (imul r9d  -> high half into edx)
    int64_t prod = (int64_t)eax * (int64_t)(int32_t)r9d;  // 0x1800034a0  imul r9d
    int32_t edx  = (int32_t)(prod >> 32);                 //              (high 32 bits)
    edx = edx + (int32_t)r9d;                     // 0x1800034a3  add edx,r9d
    edx = edx >> 7;                               // 0x1800034a6  sar edx,7   (arithmetic)
    eax = (int32_t)((uint32_t)edx >> 31);         // 0x1800034a9..ab  mov eax,edx ; shr eax,31  (sign bit)
    edx = edx + eax;                              // 0x1800034ae  add edx,eax  -> edx = r9d / 180
    edx = edx * 0xb4;                             // 0x1800034b0  imul edx,edx,180  -> edx = (quot*180)
    r9d = (int32_t)r9d - edx;                     // 0x1800034b6  sub r9d,edx  -> r9d = s % 180   (signed rem)
    // ---- end division; r9d now holds a' = (angle_a + offset) mod 180 ----

    int32_t ecx = (int32_t)r9d - (int32_t)r10d;   // 0x1800034b9..bc  mov ecx,r9d ; sub ecx,r10d  -> a' - angle_b
    if ((ecx & 0xffffffff) > 0)                   // 0x1800034bf..c1  test ecx,ecx ; jg 0x1800034c9
        goto have_abs;                            //   (ecx > 0 signed: keep it as the difference)
    ecx = (int32_t)r10d - (int32_t)r9d;           // 0x1800034c3..c6  mov ecx,r10d ; sub ecx,r9d  -> angle_b - a'
have_abs:                                         // 0x1800034c9
    eax = 0xb4 - ecx;                             // 0x1800034c9..ce  mov eax,180 ; sub eax,ecx  -> 180 - d
    if (ecx < eax)                                // 0x1800034d0  cmp ecx,eax
        eax = ecx;                                // 0x1800034d2  cmovl eax,ecx   -> min(d, 180-d)
    return eax;                                   // 0x1800034d5  ret
}
```

### Notes on the idiom
- `imul r9d` is a **one-operand signed** multiply: `edx:eax = eax * r9d`; only the
  high half (`edx`) is used afterward — the canonical `__divsi3`-by-constant pattern.
- `0xb60b60b7` (signed `-1240768329`) is the standard magic for **signed division by
  180**. The trailing `add edx,r9d ; sar edx,7 ; add (sign bit)` is the fix-up for a
  magic whose high bit forces the `+dividend` correction with shift 7.
- Because it is signed truncated division, the remainder `r9d` keeps the sign of the
  dividend. In practice `angle_a+offset` is expected non-negative, giving `a' ∈ [0,179]`.
- The two-step `ecx` computation is just `d = |a' - angle_b|` written as: assume
  `a'-b`; if that is not strictly positive, use `b-a'` instead. (Edge: if `a'==b`,
  `jg` is not taken, so `ecx = b-a' = 0` — still correct.)
- Final `min(d, 180-d)` folds the difference onto the 0..90 half-ring: orientations
  differing by ~180° are considered *close* (≈0), the classic unsigned-orientation
  metric.

## GDB verification hooks

To verify a Python port produces identical intermediate values:

- `break *0x18000349d` — **inputs latched.** Dump `$cl`=angle_a, `$dl`=angle_b,
  `$r8d`=offset. (Right before `add r9d,r8d`.) These are the three arguments.
- `break *0x1800034b6` — **after the modulo.** At this instruction `edx` = quotient
  `(angle_a+offset)/180`. After stepping one instruction (`sub r9d,edx*...`)... easier:
- `break *0x1800034b9` — **a' computed.** Dump `$r9d` = `a' = (angle_a+offset) % 180`
  (signed remainder, expect 0..179). This is the single most important intermediate.
- `break *0x1800034c9` — **raw difference.** Dump `$ecx` = `d = |a' - angle_b|`
  (before folding). Also `$r10d` here still = angle_b.
- `break *0x1800034d5` — **return.** Dump `$eax` = final `min(d, 180-d)` ∈ [0,90].
  This is the value the caller consumes (orientation-match cost / distance).

## Confidence & open questions

**Solid (verified numerically against the exact instruction sequence):**
- It computes `min(|((angle_a+offset) % 180) - angle_b|, 180 - that)`, range 0..90.
- `0xb60b60b7`/`sar 7`/sign-bit-add is signed division by **180** (checked over a
  range of inputs incl. negatives, wraparound 170↔10, and 0↔179).
- arg1/arg2 are used as **bytes**; arg3 (`r8d`) is used full-width.

**Inferred / open:**
- The *meaning* of arg3 (`offset`) is a guess: most likely a per-frame rotation (in
  whole degrees) applied to orientation A before comparison — consistent with the
  sec0_pre rigid-transform context, where frames are rotated to align. It could
  instead be a quantization/binning offset. Confirm by inspecting the call site.
- Units are assumed **degrees** because the modulus is 180 and inputs are single
  bytes. This is an *orientation* difference (180-periodic), not a full 360° heading.
- This is almost certainly a small helper used inside an orientation/descriptor
  matching loop (cost = how far apart two ridge orientations are), not transform
  math itself — but it feeds the correspondence scoring that the rigid-transform
  estimator relies on.
